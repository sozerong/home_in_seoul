# 남은 설계 과제 (2026-11-13 기준)

혼잡도와 전월세 정제를 SQL로 옮긴 뒤(결정 42, 72) 아직 정하지 않은 설계를 한곳에 모은다. 항목마다 **왜 필요한지(근거), 지금 상태, 고를 것(선택지 표), 끝났다고 보는 조건**을 적는다. 선택은 사용자가 하고, 고른 것은 `docs/decisions.md`에 결정 번호로 옮긴다. 이 문서는 선택지를 정리할 뿐 고르지 않는다.

## 1. P6 규칙 버전

**근거.** 정제가 dbt 모델이 되면서 "규칙을 고치면 다시 만들 단위를 고르는 일"은 사라졌다. 다음 빌드가 모든 수집일에 새 규칙을 적용한다(결정 62, 측정 24 S3). 남은 빈칸은 두 가지다.
- 지금 `stg_dbt.rent`의 행이 **어떤 규칙으로 만들어졌는지** 데이터에 남지 않는다.
- 규칙을 고친 뒤 **무엇이 바뀌었는지**는 측정 24처럼 일부러 빌드를 두 번 만들어야 보인다. 운영에서는 교체 때 직전 스키마(`stg_dbt_old`)가 지워진다(`macros/swap_schemas.sql`).

**지금 상태.** dbt manifest의 모델 `checksum`은 모델 파일 원문의 sha256이다. 규칙 일부가 매크로(`rent_int`, `py_strip` 등)에 있어서, 매크로만 고치면 모델 checksum은 그대로일 것으로 본다 [확인 필요: 매크로만 바꿔 checksum 비교]. 컴파일된 SQL의 해시는 매크로 변경까지 반영한다.

**고를 것 1. 버전 값**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. git 커밋 | 이미 lineage 회차가 쓴다. 사람이 읽기 쉽다 | 커밋 전 변경(작업 중 빌드)을 구별하지 못한다(10절과 같은 문제). 규칙과 상관없는 커밋에도 바뀐다 |
| B. 컴파일된 정제 SQL의 해시(모델마다) | 규칙이 실제로 바뀐 때만 바뀐다. 매크로 변경도 잡는다 | 해시만으로는 무엇이 바뀌었는지 모른다. 커밋과 이어 주는 기록이 따로 필요하다 |
| C. 규칙 번호를 사람이 관리(예: rules.md에 "rent 규칙 v3") | 뜻이 분명하다 | 올리는 것을 잊으면 틀린다. 강제할 장치가 없다 |

**고를 것 2. 기록 위치**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 행마다 컬럼(`rule_version`) | 행 하나만 봐도 안다 | 전체 재빌드라 모든 행이 늘 같은 값이다. 저장만 늘고 정보는 빌드 기록 한 줄과 같다 |
| B. 빌드마다 기록 표 한 줄(`ops.build_run`: 빌드 시각, git 커밋, 모델별 해시, 표별 행 수) | 가볍다. 운영 대시보드가 바로 읽는다 | 행에서 빌드로 가는 연결은 "지금 표 = 마지막 성공 빌드"라는 약속에 기댄다 |

**고를 것 3. 바뀐 것을 남기는 법**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 남기지 않음(지금) | 추가 비용 없음 | 정정 뒤 영향 범위를 사후에 알 수 없다 |
| B. 교체 직전에 새 빌드와 지금 표를 비교해 요약만 기록(처리 단위별 바뀐 행 수) | 저장이 작다. "규칙을 고쳤더니 58단위가 바뀜"이 자동으로 남는다 | 비교 비용이 매 빌드 든다(측정 24에서 비교 쿼리 1.1초, 전월세만). 비교할 표와 키를 정해야 한다 |
| C. `_old` 스키마를 다음 빌드까지 지우지 않고 둠 | 무엇이든 사후에 비교할 수 있다 | 디스크가 두 배. 교체 매크로를 고쳐야 한다(결정 32) |

**끝 조건.** 규칙 한 줄을 실제로 고치고 wh_load를 돌리면, 사람이 빌드를 두 번 만들지 않아도 "어느 빌드에서 어느 단위가 몇 행 바뀌었나"가 쿼리 한 번으로 나온다(S3 세 번째 측정).

## 2. P3 스키마 이력

**근거.** 모르는 키는 dbt 테스트(`congestion_raw_unknown_keys`, `rent_raw_unknown_keys`)가 경고하지만, 경고는 그 빌드의 로그에만 있고 **언제부터 모양이 바뀌었는지**는 남지 않는다. 혼잡도 분기 파일은 실제로 컬럼 이름이 바뀌어 왔다(`docs/data_sources.md` 5절).

**지금 상태.** 원본이 jsonb라(`raw.congestion`, `raw.rent`) 수집일별 키 집합은 원본에서 바로 계산된다. 원본은 지우지 않으므로 과거 이력도 다시 만들 수 있다.

**고를 것 1. 계산과 저장 방식**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 원본을 읽는 뷰(수집일 × 키 집합 해시) | 저장이 없고 늘 맞다. 과거도 바로 나온다 | 열 때마다 원본 전체를 훑는다(전월세 원본 249MB) |
| B. 원본 적재기(`*_raw.py`)가 적재 때 한 줄씩 기록하는 표 | 싸다. 처리 단위별로 남는다 | Python에 로직이 다시 생긴다. 과거분은 한 번 채워야 한다 |
| C. dbt 모델(표)로 빌드마다 다시 만든다 | 규칙이 SQL 한곳에 있고 리니지에도 나온다. 결정 62와 같은 방식 | 빌드 시간이 는다(A와 같은 훑기를 빌드마다) |

**고를 것 2. 단위**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. (출처, 수집일)마다 키 합집합 하나 | 단순하다 | 한 수집일 안에서 일부 item만 키가 다른 경우(예: 일부 페이지)를 놓친다 |
| B. (출처, 수집일, 키 집합)마다 item 수 | 섞여 들어온 모양까지 보인다 | 행이 조금 는다. 전월세는 offi와 rh가 원래 키가 달라 출처 구분을 함께 둬야 한다 |

**범위.** 원본이 jsonb인 출처(지금 2개)만 할지, Python 정제가 남은 출처(필드 집합이 다르면 실패하는 F1 방식)는 5절 이전 뒤로 미룰지도 함께 정한다.

**끝 조건.** 같은 수집일을 두 번 넣어도 이력이 한 줄이다(멱등). 키가 다른 입력을 넣으면 새 해시와 그 날짜가 남는다.

## 3. P5 상품 계약 변경 정책

**근거.** `product/v*/manifest.json`에는 행 수와 sha256만 있고 컬럼 이름·타입이 없다. 받는 쪽(부동산 플랫폼, 결정 12)은 "이번 버전이 나를 깨뜨리나"를 알 수 없다. 상품 버전은 내보낸 날짜다.

**고를 것 1. 검사 수단**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. dbt 모델 계약(`contract: enforced`)을 마트 4표에 | 빌드 전에 컬럼·타입을 검사한다. not_null 등 제약도 건다 | 지금 버전(dbt-core 1.12.6, dbt-postgres 1.11.0)과 빌드 스키마 교체(결정 32)에서 함께 되는지 [확인 필요: 실행으로]. 버전 없는 모델은 깨는 변경이 경고뿐이다(dbt 문서, 2026-11-11 확인) |
| B. `export_product.py`가 manifest에 스키마를 쓰고 직전 버전과 비교 | 받는 쪽이 보는 파일 기준이라 정확하다. 도구 의존이 없다 | 비교 코드를 직접 쓴다. 빌드가 끝난 뒤에야 안다 |
| C. A + B | 빌드 전과 내보내기 두 군데서 잡는다 | 같은 규칙이 두 곳에 생긴다 |

**고를 것 2. 깨는 변경(컬럼 삭제, 이름 변경, 타입·단위 변경)일 때**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 내보내기 실패 | 받는 쪽이 깨질 일이 없다 | 의도한 변경도 막혀 계약 문서를 먼저 고치는 절차가 필요하다 |
| B. 내보내되 버전 규칙을 바꿈(예: 날짜 + 주 버전 올림)과 변경 기록 | 흐름이 멈추지 않는다 | 받는 쪽이 버전을 읽어야 안전하다 |

**고를 것 3. 리니지와 잇는 순서.** 깨는 변경이 어느 원천에서 왔는지 적으려면 내보내기가 리니지를 읽어야 하는데, 지금 lineage DAG는 내보내기 **뒤에** 돈다(결정 50, 57).

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 내보내기는 직전 리니지 회차를 읽음 | 순서를 안 바꾼다 | 이번 코드 변경이 지도에 아직 없을 수 있다(stale) |
| B. wh_load 안에서 내보내기 전에 리니지 추출 | 지도가 늘 이번 코드와 맞다 | wh_load가 길어지고, 리니지 실패가 상품을 막을지 정해야 한다(결정 50은 막지 않기로 함) |
| C. 원천 추적은 lineage DAG가 끝난 뒤 별도 기록으로 덧붙임 | 순서와 실패 범위가 그대로 | 상품과 원천 설명이 따로 나온다 |

**끝 조건.** 마트 컬럼 하나를 바꾼 실험에서 깨는 변경이 자동으로 판정되고(S4 재측정), `docs/data_contract.md`에 변경 정책 절이 생긴다.

## 4. P7 알림 경로

**근거.** 지금 사람에게 닿는 것은 작업 실패(`dags/alerting.py`, `logs/alerts.log`, `ops.failure_log`)뿐이다. 다음 세 가지는 화면을 열어야 보인다.
- dbt 경고(모르는 키 등). 결정 63, 73에서 "P7에서 다룬다"로 미뤘다.
- 출처 늦음(`ops.freshness`).
- Airflow가 꺼져 있어 아예 돌지 않은 것(S5, 측정 11). Airflow 안의 콜백으로는 알 수 없다.

**고를 것**

| 항목 | 선택지 |
|---|---|
| 닿는 곳 | 슬랙 웹훅 / 이메일 / 그 밖 (CLAUDE.md 단계 7은 둘 중 하나) |
| "실행 안 됨" 검사 위치 | Airflow 안의 감시 DAG(Airflow가 살아 있을 때만 의미) / Airflow 밖(Windows 작업 스케줄러 등) [확인 필요: PC가 꺼져 있으면 둘 다 못 돎] |
| 경고를 실어 나르는 법 | dbt 실행 결과(`run_results.json`)에서 warn을 읽어 보냄 / 운영 뷰에 경고 표를 두고 감시가 읽음 |
| S5 목표 시간 | 사용자가 정한다(측정 11의 기준값과 비교) |

**끝 조건.** 일부러 넣은 실패·지연·경고가 실제로 도착하고, 신호마다 플레이북 한 항목(무엇을 보고 무엇을 하나)이 있다. S5를 다시 재서 "멈춘 뒤 사람이 알기까지"가 줄었다.

## 5. 남은 출처의 SQL 이전

**근거.** S6a(편의 업종 추가, 측정 17)와 S6b(저녁 귀가 18~20시, 측정 18)의 목표는 "꺼내는 SQL만 고침"인데, 두 요구가 걸린 출처(상가정보, 생활이동)는 아직 Python 정제다. 옮기지 않으면 S6을 다시 잴 수 없다.

**지금 상태.**

| 출처 | 정제 | 크기 | 옮길 때 걸리는 점 |
|---|---|---|---|
| 상가정보 | `transform/sbiz_store.py`, 6코드만 stg에 | stg 30,394행, 서울 원본 554,092행 | 원본 전체를 jsonb로 담으면 행이 18배. 그래야 S6a가 "SQL만 고침"이 된다 |
| 생활이동 | `transform/living_migration.py` + Iceberg(결정 35) | stg 40,382,008행, 8,972MB | 원본을 PostgreSQL jsonb로 담으면 매우 크다. 24시간 원본은 이미 Iceberg에 있다 |
| 역사마스터 | `transform/station_master.py` | 작음 | 걸리는 점 적음. 다만 S 시나리오에 걸린 요구가 없다 |
| 행정동 경계, 연속지적도 | `transform/boundary.py` (shp, PostGIS) | 연속지적도 896,692필지 | 도형은 jsonb 원본 모양과 맞지 않는다 |

**고를 것 1. 범위**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 상가정보만 더 옮김 | S6a를 다시 잴 수 있다. 크기가 감당할 만하다 | S6b는 기준값으로 남는다 |
| B. 상가정보 + 생활이동 | S6 두 개를 모두 다시 잰다 | 생활이동 원본 모양을 새로 정해야 한다(아래 2) |
| C. 여기서 멈춤(2개 출처를 본보기로) | 이후 P6·P3·P5에 집중 | 출처마다 방식이 섞인 상태가 남고 S6은 기준값뿐이다 |

**고를 것 2. 생활이동을 옮긴다면 원본 모양**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. PostgreSQL `raw` jsonb(다른 출처와 같음) | 방식이 하나 | 4천만 행 이상, 전체 재빌드(결정 62)와 맞지 않는다 |
| B. 넓은 원본 표(text 컬럼) + 증분 빌드 | jsonb보다 작다 | 새 필드에 약해진다(결정 60의 A와 같은 단점) |
| C. Iceberg를 원본으로 두고 꺼내는 쪽만 SQL(Spark SQL 또는 DuckDB) | 이미 있는 층을 쓴다. 24시간 전체가 있다 | dbt(PostgreSQL)와 엔진이 둘로 나뉘고 리니지 추출 대상이 늘어난다 |

**끝 조건.** 옮긴 출처마다 옛 결과와 차이 0(설계서 2.6), 해당 S6을 다시 잰다.

## 6. blue/green 실패 범위

**근거.** 정제가 dbt로 오면서 출처 하나의 검사가 실패하면 그 회차 wh_load 전체(모든 출처 갱신과 상품)가 멈춘다. 결정 63(혼잡도), 결정 73 2번(전월세 F2)에서 대가로 받아들였다. 옛 구조에서는 그 출처, 그 처리 단위만 실패했다. 출처를 더 옮길수록(5절) 멈출 일이 는다.

**고를 것**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 지금 유지(전부 아니면 전무) | 결정 30 D2와 같다. 상품이 늘 한 시점으로 일관된다 | 출처가 늘수록 한 출처 때문에 전체가 늦어진다 |

| C. 단위 제외: 기준을 넘은 처리 단위만 하류에서 빼고 경고(옛 F2와 같은 효과) | 나머지는 계속 갱신된다 | 경고가 사람에게 닿아야 의미가 있다(4절 먼저). 모델 SQL에 제외 조건이 는다 |

## 8. `stg_dbt` 이름 정리

**근거.** 결정 61로 dbt 정제 결과는 `stg_dbt`, Python 정제 결과는 `stg`에 있다. 결정 61은 "모든 출처가 옮겨지면 `stg`로 합칠지 그때 정한다"고 했다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 5절이 끝난 뒤 `stg`로 합침 | 층 이름이 하나 | 남은 Python 표(경계 등)와 이름이 겹치지 않게 정리해야 한다. 운영 카드, 리니지 정답, 문서의 표 이름을 모두 고친다 |
| B. 계속 나눠 둠(`stg` = Python, `stg_dbt` = SQL) | 어느 방식인지 이름으로 안다 | 받는 쪽 문서와 지도에 층이 두 개로 보인다 |

5절 범위가 정해진 뒤 고른다.

## 9. 전체 재빌드의 한계선

**근거.** 결정 62는 매번 전체 재빌드를 골랐고 "느려지면 incremental로 바꾼다"고만 했다(설계서 U6). 지금 값: wh_load dbt 전체 133.8초, 전월세 정제 표 9.1초, 혼잡도 1.1초(측정 23, 24, 1회씩). 혼잡도는 한 주에 65,169행, 전월세는 수집 한 번에 원본이 그만큼 는다(수집일별 통과 행 20,109~70,546, 최근 세 번 44,308~47,847. 매주 최근 3개월을 다시 받기 때문이다).

**고를 것.** 바꿀 기준(예: wh_load `dbt_build`가 N분을 넘으면, 또는 정제 표 하나가 M초를 넘으면)과, 넘었을 때의 방식(수집일 단위 delete+insert, 또는 최근 K개 수집일만 남기고 옛 수집일은 요약). 기준은 측정으로 지켜볼 수 있게 운영 카드에 빌드 시간을 둘지도 함께 정한다.

# 정제와 검증 규칙 (단계 4)

출처마다 정제 규칙(값의 모양을 고침)과 검증 규칙(값이 말이 되는지 봄)을 먼저 합의한 뒤 코드로 옮긴다. 검증에 어긋난 행은 버리지 않고 격리 테이블에 사유와 함께 남긴다.

## 1. 전월세 실거래가 (오피스텔 + 연립다세대)

상태: **합의됨 (2026-10-21).** 근거는 data_sources.md 1, 2, 14절과 measurements.md 측정 4.

### 정제 규칙
| # | 대상 | 규칙 | 근거 |
|---|---|---|---|
| C1 | 두 출처 합치기 | 오피스텔과 연립다세대를 한 표로. offiNm, mhouseNm → building_name. 출처 구분 컬럼(offi / rh) 추가. 연립다세대의 houseType은 그대로 둔다 | 두 API는 필드 이름만 다르다 |
| C2 | 모든 문자열 | 앞뒤 공백 제거. 공백 한 칸(" ")은 NULL | 빈 값이 " "로 온다 |
| C3 | 금액 4개 (deposit, monthlyRent, preDeposit, preMonthlyRent) | 쉼표 제거 후 정수. 단위는 만원 그대로 | "24,500" 형태 |
| C4 | 계약일 | dealYear, dealMonth, dealDay → 날짜 하나 | 세 칸으로 나뉘어 온다 |
| C5 | 면적, 층, 건축년도 | 숫자로. 층은 음수(지하) 유지 | 연립다세대에 지하층 -1 |
| C6 | 위치 | sggCd + umdNm → 법정동 코드 10자리. jibun → 본번, 부번 → PNU 19자리(대지구분 1) | 강남 607개 모두 PNU를 만들었고 연속지적도에서 모두 찾음 |
| C7 | 수집 정보 | 수집일, 원본 파일 이름을 컬럼으로 남긴다 | 단계 6 증분 적재와 추적 |
| - | contractTerm | 풀지 않고 그대로 둔다 | 질문에서 쓰지 않는다 |

- **완전히 같은 행은 모두 남긴다.** 동·호가 없어 다른 호실의 계약인지 중복 신고인지 구별할 수 없고, 단계 1에서 본 사례(같은 날·같은 층·같은 조건의 신축 오피스텔 계약)는 다른 호실일 가능성이 높다. 원본 건수(totalCount)와도 맞는다. 이것은 한 번의 수집 안에서의 규칙이고, 여러 수집일에 같은 거래가 다시 나오는 문제는 단계 6에서 다룬다.
- **법정동 이름 → 코드 대응표는 상가정보(서울 202606)의 (시군구코드, 법정동명, 법정동코드)에서 만든다.** 상가가 없는 법정동은 빠질 수 있다. 빠지면 V8로 격리되어 숫자로 드러나며, 그때 공식 법정동 코드표를 받는다.

### 검증 규칙 (행 단위, 어긋나면 격리)
| # | 검사 | 어긋나는 경우 |
|---|---|---|
| V1 | 필수값 | deposit, monthlyRent, 계약일, excluUseAr, umdNm, jibun 중 하나라도 NULL |
| V2 | 계약년월 | 계약일의 년월이 요청한 DEAL_YMD와 다름 |
| V3 | 날짜 | 존재하지 않는 날짜 |
| V4 | 금액 범위 | 보증금 또는 월세가 음수 |
| V5 | 면적 범위 | 전용면적 0 이하 또는 300㎡ 초과 |
| V6 | 층 범위 | -5 미만 또는 80 초과 |
| V7 | 계약 종류 | contractType이 신규, 갱신, NULL 외의 값 |
| V8 | 법정동 코드 | umdNm을 법정동 코드로 바꾸지 못함 |
| V9 | 지번 모양 | 본번-부번 숫자 모양이 아님 |

- 정제 규칙을 적용하지 못한 값(예: 숫자 칸에 숫자가 아닌 값)은 그 **정제 규칙 번호**(C3 금액, C4 계약일, C5 면적·층·건축년도)를 격리 사유로 남긴다. 합의한 V1~V9에 "형식 오류"가 없어서 구현할 때 더했다(2026-10-21).
- 구현: transform/rent.py. 처리 단위(출처, 수집일, 구, 계약년월)마다 두 테이블의 기존 행을 지우고 다시 넣는 것을 한 트랜잭션으로 한다.

### 파일 단위 검사 (어긋나면 그 파일 처리 전체를 실패)
| # | 검사 |
|---|---|
| F1 | 필드 집합이 예상과 다름 (스키마 변경) |
| F2 | 격리 비율이 5% 초과. 구현 후 지금 받은 파일들로 실제 비율을 재고 조정한다 |

- 실측 (2026-10-21 수집분, 강남구 오피스텔·연립다세대 202609·202610, 4개 처리 단위, 1,032행): **격리 0건(0.00%)**. 기준 5%는 그대로 둔다. 다른 구를 처리하면서 다시 본다.

## 2. 서울시 역사마스터

상태: **합의됨 (2026-10-21).** 근거는 data_sources.md 4절.

입력 확인: API 파일(subwayStationMaster_p001.xml)과 손으로 받은 CSV가 784행 중 783행 같다. 다른 1행(역사_ID 3109)은 CSV가 가운뎃점을 "?"로 잃었고 API는 "아라(북부법원·검찰청)"로 제대로 담았다. 좌표가 완전히 같은 행이 3묶음 있다(환승역에서 호선마다 같은 좌표를 쓴 것으로 보임 [확인 필요]). 규칙으로 막지 않고 기록만 한다.

처리 단위: **수집일 하나**(역 전체 목록). **수집일마다 스냅샷을 모두 남긴다.** 역 개명이 언제 반영되는지 추적하기 위해서다. 쓰는 쪽(단계 5)은 가장 최근 수집일을 고른다.

### 정제 규칙
| # | 대상 | 규칙 | 근거 |
|---|---|---|---|
| SC1 | 입력 | API로 받은 subwayStationMaster_p*.xml을 읽는다 | CSV는 CP949라 가운뎃점을 잃는다 |
| SC2 | 역사_ID | 문자 4자리 그대로 둔다 | 앞자리 0("0150") 보존. 혼잡도 역번호와 잇는 열쇠 |
| SC3 | 좌표 | 위도, 경도를 숫자로. 좌표계 변환과 점(geometry)은 단계 5에서 만든다 | 공간 처리는 PostGIS에서 한 번에 |
| SC4 | 수집 정보 | 수집일, 원본 파일 이름, 파일 안 순번 | 추적 |
| - | 역 이름, 호선 이름 | 그대로 둔다 | 혼잡도와는 역번호로 잇는다. 이름 맞추기가 필요한 승하차는 쓰지 않는다(결정 6) |
| - | 서울 밖 역 | 그대로 둔다 | 서울 경계 근처에서는 경기 쪽 역이 가장 가까울 수 있다. 걸러야 하면 단계 5에서 공간으로 판단 |

### 검증 규칙 (행 단위, 어긋나면 격리)
| # | 검사 | 어긋나는 경우 |
|---|---|---|
| SV1 | 필수값 | BLDN_ID, BLDN_NM, ROUTE, LAT, LOT 중 하나라도 비어 있음 |
| SV2 | 역사_ID 모양 | 숫자 4자리가 아님 |
| SV3 | 좌표 | 숫자가 아니거나 위도 33~39, 경도 124~132 밖(위도·경도 뒤바뀜 포함) |

### 파일 단위 검사 (어긋나면 전체 실패)
| # | 검사 |
|---|---|
| SF1 | 필드 집합이 BLDN_ID, BLDN_NM, ROUTE, LAT, LOT와 다름 |
| SF2 | 역사_ID 중복 |
| SF3 | 격리 비율 5% 초과 |
| SF4 | 직전 수집일 스냅샷보다 행 수가 10% 넘게 줄어듦. 직전 스냅샷이 없으면 건너뛴다. 완결성 검사(list_total_count)는 API 스스로 건수를 적게 말하면 잡지 못하므로 그 빈틈을 막는다 |

- 구현: transform/station_master.py, warehouse/sql/02_stg_station_master.sql(기본 키 (collected_date, bldn_id)), 시험 tests/test_station_master.py.
- 실측 (2026-10-21 수집분): row 784, 통과 784, **격리 0건(0.00%)**. 두 번 실행해도 784행. 역사_ID 0150은 앞자리 0이 유지되고, 3109는 가운뎃점이 그대로 들어왔다.
- 시험: SV1~SV3와 겹치는 경우(좌표가 비면 SV1만), 위도·경도 뒤바뀜을 확인했다. 좌표 범위 검사를 일부러 넓힌 변형 코드로 돌리면 시험이 실패하는 것도 확인했다.
- **미확인**: SF4는 DB에 이전 수집일 스냅샷이 있어야 동작한다. 다른 날 다시 수집할 때 "통과" 경로를 처음 지나가고, "급감으로 실패" 경로는 아직 실행된 적이 없다.

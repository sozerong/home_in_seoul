# 지시서: 공개 사이트 배포를 손으로 하지 않게 만들기

Claude Code가 읽고 처음부터 끝까지 진행하는 지시서다. 2026-11-22에 썼다.

## 진행 방식

`docs/handoff_portal.md`의 "진행 방식" 1~4번을 그대로 따른다. 요약하면 아래와 같다.
- 승인을 기다리지 않고 끝까지 진행한 뒤 한 번 보고한다.
- 간단한 일은 바로 한다.
- 고를 것이 있으면 당근 테크 블로그 도입기처럼 후보를 두고 비교한 뒤 직접 고르고, `docs/decisions.md`에 결정으로 남긴다. 결정 머리에 "사용자 위임(2026-11-22 지시), Claude Code가 고름"이라고 적는다.
- 모든 주장에 근거(파일과 행, 실행한 명령과 결과, 공식 문서 URL과 확인 날짜)를 단다. 확인할 수 없으면 `[확인 필요]`로 둔다.

이번 일에서는 5번(사용자 손이 필요한 것)을 아래처럼 바꾼다.
- **자동 푸시를 만드는 것 자체가 이번 일이다.** 사용자가 직접 지시했다(2026-11-22: "매번 직접 올려야 하나, 메인 레포 작업하면 자동으로 되게"). 그래서 Claude Code는 자동으로 커밋·푸시하는 워크플로나 태스크를 만든다. 다만 Claude Code가 지금 이 작업을 하면서 직접 커밋·푸시하지는 않는다.
- 사용자가 하는 일은 아래로 정한다. 보고서 5번에 단계별 클릭 경로까지 적는다.
  - 토큰이나 배포 키 만들기, GitHub Secrets 등록, `.env` 값 넣기(값은 사용자가 넣는다. 지시서·보고·로그에 값을 쓰지 않는다)
  - 레포 설정 바꾸기(Pages 소스, Actions 권한, 브랜치 규칙)
  - PR 머지와 첫 실행 확인
  - 파일 지우기

## 0. 한 줄 요약

지금은 코드 레포(sozerong/home_in_seoul)에서 사이트 문구를 고쳐도 공개 사이트(https://sozerong.github.io/home_in_seoul-data/)에 저절로 반영되지 않는다. 사용자가 매번 PC에서 4단계를 손으로 한다. 이것을 "코드 레포 main에 머지하면 사이트가 바뀐다"와 "새 데이터 버전이 나오면 공개된다"로 바꾼다.

## 1. 지금 상태 (사실과 근거)

| 사실 | 근거 |
|---|---|
| 두 레포 사이에 자동 연결이 없다. 배포는 사용자가 `publish_site` 실행, `cd`, `git add/commit/push`를 손으로 한다 | README.md 169~178행 |
| 2026-11-22에 실제로 막혔다. 사용자가 코드 레포만 커밋하고 데이터 레포는 안 올라간 줄 몰랐고, 셸(cmd, PowerShell)에 따라 가상환경 명령이 달라 다시 물었다 | 이 지시서를 만든 대화 |
| `product/`는 git에 없다. GitHub Actions 러너에는 상품 버전 폴더가 없다 | .gitignore(`product/`) |
| `publish(version, out)`은 `product/<버전>/`을 읽어 공개 버전 폴더를 만든 뒤 사이트 파일을 다시 만든다 | warehouse/publish_site.py 382~388행 |
| 사이트 파일만 다시 만드는 `site_files(out, cfg, contract)`는 `product/`를 읽지 않는다. 읽는 것은 `--out`의 공개 버전 폴더, `docs/public_columns.json`, `docs/product_contract.json`, `docs/data_contract.md` 3절, `warehouse/site/index.html`뿐이다 | publish_site.py 306행부터. 실제로 그런지 함수 안을 끝까지 읽고 확인한다 |
| 지금 CLI에는 "사이트만 다시 만들기"가 없다. `--version`과 `--out`이 둘 다 있어야 한다 | publish_site.py 515~525행 |
| 새 데이터 버전은 로컬 Airflow `wh_load` DAG의 `export_product` 태스크가 `product/v{오늘}/`에 만든다 | dags/wh_load.py 9, 40~41행 |
| 코드 레포에는 CI가 있다(검사만 하고 배포는 하지 않는다) | .github/workflows/ci.yml |
| 코드 레포 main에는 ruleset이 있어 브랜치와 PR로만 들어간다. 데이터 레포 main의 규칙은 모른다 | 2026-11-22 확인 / [확인 필요] |
| 같은 입력이면 같은 바이트가 나오고, 공개 버전 폴더는 불변이다. 다르면 아무것도 쓰지 않고 실패한다 | publish_site.py 1~21행 docstring, selftest 1·4번 |
| 데이터 레포에는 `.gitattributes`(`* -text`)가 있다. 없으면 Windows git이 CSV 줄바꿈을 바꿔 sha256이 틀어진다 | publish_site.py 376~377행 주석 |

바뀌는 일은 두 종류이고, 데이터가 있는 곳이 다르다.

| 종류 | 예 | 필요한 입력 | 입력이 있는 곳 |
|---|---|---|---|
| (1) 사이트 변경 | 화면 문구, 컬럼 설명, 출처 화면 | 코드 레포 파일 + 데이터 레포의 기존 공개 버전 폴더 | 둘 다 GitHub에 있다 |
| (2) 새 데이터 버전 | Airflow가 `product/v2026.12.01/`을 만듦 | `product/<버전>/` | 사용자 PC에만 있다 |

## 2. 할 일

### D1. "사이트만 다시 만들기" 모드를 만든다 (간단한 일, 바로 한다)

- `publish_site.py`에 `product/` 없이 `--out`의 기존 공개 버전 폴더로 사이트 파일만 다시 만드는 실행 방법을 더한다(예: `--site-only --out <폴더>`). 이름은 Claude Code가 정한다.
- 이 모드는 공개 버전 폴더(`vYYYY.MM.DD/`)를 절대 바꾸지 않는다. 실행 전후 `tree_hashes`로 버전 폴더를 비교하고, 하나라도 다르면 실패한다.
- `product/` 없이 도는 확인을 하나 남긴다(selftest에 번호를 더하거나 별도 `--selftest-site`). CI 러너에는 `product/`가 없으므로, CI에서 돌 검사는 이것이어야 한다.
  - 같은 입력으로 두 번 만들면 같은 바이트인지
  - 버전 폴더가 바뀌지 않았는지
  - 정적 요약에 비공개 컬럼이 이름·사유 목록 밖에 나오지 않는지(selftest 2d와 같은 검사)
  - 이 버전의 비공개 컬럼마다 `display_reason`이 있는지

### D2. 사이트 변경 (1)을 자동 배포한다 (후보 비교 후 직접 고른다)

문제: 코드 레포 main에 사이트 관련 파일이 머지되면, 사람 손 없이 데이터 레포의 사이트 파일이 다시 만들어지고 Pages에 반영돼야 한다.

후보(더 있으면 넣는다):

| 후보 | 내용 | 확인할 것 |
|---|---|---|
| A. 그대로 둔다 | README 순서를 손으로 | 오늘 실제로 막힌 기록 |
| B. 코드 레포 Actions가 데이터 레포에 푸시 | main 푸시(경로 필터) → 데이터 레포 checkout → D1 실행 → 바뀐 게 있을 때만 커밋·푸시 | 기본 `GITHUB_TOKEN`으로 다른 레포에 푸시할 수 있는지(GitHub 공식 문서). 안 되면 fine-grained PAT(데이터 레포 contents 쓰기만)나 deploy key 중 무엇이 범위가 좁은지 |
| C. 데이터 레포 Actions가 코드 레포를 읽어 스스로 갱신 | 데이터 레포 워크플로가 공개 코드 레포를 checkout(토큰 불필요한지 확인) → D1 실행 → 자기 레포에 `GITHUB_TOKEN`으로 푸시. 시작 신호는 `repository_dispatch`, `schedule`, `workflow_dispatch` 중에서 고른다 | 비밀 값 없이 되는지, 반영까지 걸리는 시간, 코드 레포의 어느 커밋으로 만들었는지 기록되는지 |
| D. Pages를 "GitHub Actions" 소스로 바꾸고 사이트 파일을 커밋하지 않음 | 데이터 레포에는 버전 폴더만 두고, 사이트 파일은 Pages 아티팩트로만 배포 | Pages 설정 변경, 데이터 레포만 clone한 사람이 사이트 파일을 못 보는 문제, 되돌리기 |

평가 기준:
- 비밀 값이 필요한가, 필요하면 권한 범위가 얼마나 좁은가
- 같은 입력이면 같은 바이트가 유지되는가(바뀐 게 없으면 커밋을 만들지 않는가)
- 실패가 드러나는가(빨간 X, 메일)
- 공개 버전 폴더를 건드릴 길이 아예 없는가
- 두 실행이 겹칠 때 안전한가(`concurrency`)
- 레포 규칙(ruleset)과 충돌하지 않는가
- 더하는 파일 수, 사용자가 할 설정 수

워크플로가 지켜야 할 것(어느 후보든):
- `.gitattributes`가 있는 상태에서 커밋한다. 러너가 Linux여도 확인한다.
- 커밋 메시지에 만든 코드 레포 커밋 SHA를 넣는다(어느 코드로 만든 사이트인지 거꾸로 찾을 수 있게).
- 바뀐 게 없으면 커밋하지 않고 성공으로 끝낸다.
- 공개 버전 폴더에 변경이 하나라도 있으면 푸시하지 않고 실패한다(D1의 검사와 별도로 `git diff`로 한 번 더).
- 토큰 값을 로그에 찍지 않는다.

### D3. 새 데이터 버전 (2)의 공개 (후보 비교 후 직접 고른다)

문제: `product/<버전>/`은 사용자 PC에만 있다. 공개 버전 폴더는 불변이라 한 번 올라간 잘못된 버전은 지울 수 없고, 다음 버전으로만 덮을 수 있다.

후보:

| 후보 | 내용 |
|---|---|
| A. 손으로 둔다 | 새 버전만 사용자가 README 순서로 올리고, 사이트 변경은 D2가 맡는다 |
| B. Airflow 태스크가 공개까지 | `export_product` 뒤 태스크가 데이터 레포 clone에 publish하고 커밋·푸시. 컨테이너에 git, 데이터 레포 마운트, `.env`의 토큰이 필요하다 |
| C. Airflow는 만들기까지, 푸시는 한 번 누르기 | 태스크가 publish와 커밋까지 하고, 푸시는 사용자가 Airflow 화면이나 명령 하나로 |
| D. 그 밖의 방법 | 예: 상품 파일을 GitHub Release에 올려 D2의 워크플로가 받아 가기 |

평가 기준: D2의 기준에 더해, 불변인 공개 폴더에 잘못된 버전이 들어갈 위험과 그것을 막는 관문(품질 검사 결과, selftest, 비공개 컬럼 값이 없는지)을 본다.
- "공개 범위 판정(`public` 값)은 사용자"라는 규칙(handoff_portal.md 진행 방식 5번)은 그대로다. 자동 공개를 고르더라도 `public_columns.json`은 자동으로 바꾸지 않는다.
- 지금 Airflow 컨테이너가 어디에 무엇을 마운트하는지는 docker-compose.yml에서 확인하고 근거로 적는다.

### D4. 문서

- README.md 5절(169~178행)의 배포 순서를 고른 방식에 맞게 다시 쓴다. 손으로 할 일이 남으면 cmd와 PowerShell 양쪽 명령을 적는다(사용자는 Cmder의 cmd를 쓴다. 가상환경은 cmd `.venv\Scripts\activate.bat`, PowerShell `.venv\Scripts\Activate.ps1`).
- `docs/data_contract.md` 15행(공개 사이트 줄)에 배포 방식 한 줄을 더한다.
- `docs/guarantees.md`에 "자동 배포는 공개 버전 폴더를 바꾸지 않는다"를 증명 방법, 강도(매 실행 강제인지), 한계와 함께 적는다.
- 막힌 오류는 `docs/failure_analysis.md`에 원인까지 적는다.

## 3. 다 됐다고 보는 기준

로컬에서 Claude Code가 확인할 것:
1. D1 모드를 같은 입력으로 두 번 돌리면 바이트가 같고, 버전 폴더 해시가 그대로다.
2. 버전 폴더 파일 하나를 일부러 바꾼 사본에서 D1 모드를 돌리면 실패하고 아무것도 쓰지 않는다.
3. 기존 `python -m warehouse.publish_site --selftest`가 계속 통과한다.
4. 워크플로 YAML 문법 검사(가능하면 `actionlint`. 설치할 수 없으면 이유를 적는다).

사용자 머지 뒤 확인할 것(보고서에 순서로 적는다):
5. 화면 문구 한 글자를 바꾼 PR을 머지하면, 몇 분 안에 데이터 레포에 봇 커밋이 생기고 공개 사이트에 반영된다. 걸린 시간을 적는다.
6. 바뀐 게 없는 머지(예: README만 수정)에는 봇 커밋이 생기지 않는다.
7. 실패하면 Actions에 빨간 X가 뜨고 데이터 레포는 그대로다.

## 4. 하지 않을 것

- 공개 버전 폴더를 지우거나 다시 쓰지 않는다.
- `public_columns.json`의 `public` 값을 바꾸지 않는다.
- 토큰 값을 파일, 로그, 보고에 쓰지 않는다.
- `.env`, `lake/`, `product/`를 git에 올리지 않는다.
- 쓰는 곳 없는 설정이나 "나중을 위한" 워크플로를 만들지 않는다.

## 5. 마지막 보고 형식 (한 번만)

1. 바꾼 파일과 바꾼 이유: 파일마다 한 줄, 근거 포함
2. 직접 고른 것: 결정 번호, 후보, 고른 것, 핵심 근거 한 줄(D2, D3 각각)
3. 확인 결과: 3절 1~4의 명령과 결과
4. `[확인 필요]`로 남은 것: 무엇을 확인하려 했고 왜 못 했는지
5. 사용자 할 일:
   - 커밋할 파일 목록과 cmd 명령
   - 토큰·Secrets·레포 설정을 하는 클릭 경로(값은 사용자가 넣는다)
   - 머지 뒤 3절 5~7번 확인 순서

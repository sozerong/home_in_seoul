## 1. 멘토 의견 (이 프로젝트 관련)

### 방향성
- 멘토가 생각하는 플랫폼은 모델러나 분석가가 데이터를 쉽게 쓸 수 있게 도구나 환경을 제공하는 쪽이다.
- 서울 동네 찾기는 원천 데이터를 받아 가공하는 파이프라인에 가까워서 플랫폼 방향과는 조금 달라 보인다.

### DuckDB
- 아직 내부를 이해하고 썼다고 말하기에는 부족하다.
- 다음을 이해하고 있으면 좋겠다.
  1. 왜 spill(디스크로 내리기)이 안 되는지
  2. 왜 메모리가 계속 쌓이는지
  3. 새 프로세스로 띄우면 왜 해결되는지

### 면접관이라면
- DuckDB OOM부터 물어보고, spill 같은 질문을 이어 가며 어디까지 답하는지 본다.
- OOM이 났을 때 다른 DB도 생각해 봤는지 묻는다.
- 모르는 질문이 나왔을 때 어떻게 대처하는지도 본다.
- 현업에서는 DuckDB를 많이 쓰지 않아서 왜 DuckDB를 골랐는지도 질문받을 수 있다.

## 2. 해석과 할 일

멘토 의견이 아니라 정리하면서 붙인 해석이다. 가설은 `[확인 필요]`로 표시한다.

### 2.1 DuckDB OOM (가장 먼저)

**지금 이야기의 약점**: "OOM 발생 → 배치 단위 처리 + 계산 컨테이너 분리 → 해결"은 원인을 찾은 것이 아니라 피해 간 것으로 읽힌다. 특히 멘토의 세 번째 질문이 단서다. 쿼리 하나에 필요한 메모리가 한도를 넘은 것이라면 새 프로세스에서도 똑같이 터져야 한다. 새 프로세스에서 괜찮았다면 원인은 "누적"일 가능성이 있다. `[확인 필요]`

**세 질문에 대한 가설과 확인 방법**

| 질문 | 가설 | 확인 방법 |
|---|---|---|
| 왜 spill이 안 됐나 | DuckDB는 디스크로 내릴 수 있는 엔진이지만, 공식 문서에 따르면 list(), string_agg()처럼 상태 전체를 메모리에 들고 있어야 하는 집계, 블로킹 연산자가 여러 개 겹친 쿼리, PIVOT 등은 메모리가 부족해질 수 있다. 또 일부 연산은 버퍼 매니저를 거치지 않아 memory_limit보다 더 잡을 수 있다 `[확인 필요: 이 프로젝트 쿼리에 해당하는지]` | 터진 쿼리의 실행 계획(EXPLAIN ANALYZE)에서 어떤 연산자가 메모리를 잡는지 확인. temp_directory 설정과 실제 임시 파일 생성 여부 확인 |
| 터진 주체가 누구인가 | DuckDB가 스스로 멈춘 것(OutOfMemoryException)인지, 커널이 프로세스를 죽인 것(OOM killer)인지에 따라 원인이 완전히 다르다. memory_limit 기본값(시스템 메모리의 80%)이 컨테이너 한도가 아니라 호스트 RAM 기준으로 잡혔다면, DuckDB는 여유가 있다고 보는데 커널이 먼저 죽인다 `[확인 필요]` | 당시 오류 메시지와 컨테이너 종료 코드(137 여부) 확인. 컨테이너 안에서 `SELECT current_setting('memory_limit')` 값과 컨테이너 메모리 한도 비교 |
| 왜 계속 쌓이나 | 같은 프로세스에서 작업을 여러 번 돌리면 버퍼 캐시, 파이썬 쪽에 남은 결과 객체, 메모리 할당기가 해제한 메모리를 OS에 바로 돌려주지 않는 문제가 겹칠 수 있다 `[확인 필요]` | 작업마다 프로세스 RSS와 `duckdb_memory()` 값을 기록해 비교. 연결을 닫은 뒤에도 RSS가 내려가는지 확인 |
| 새 프로세스가 왜 해결하나 | 프로세스가 끝나면 그 프로세스가 잡고 있던 메모리를 OS가 전부 회수한다. 위의 누적 원인이 한꺼번에 초기화된다 | 같은 작업을 같은 프로세스에서 N번 vs 매번 새 프로세스로 N번 돌려 RSS 변화 비교 |

**다시 쓸 이야기의 순서**

1. OOM 형태 확인 (누가 죽였나)
2. 원인 확인 (어떤 연산, 어떤 누적)
3. 원인에 맞춘 해결 (설정, 쿼리, 배치 단위)
4. 그래도 계산과 스케줄러가 한 프로세스에 있으면 영향 범위가 Airflow 전체라서 분리

컨테이너 분리는 "영향 범위를 막는 설계"로는 맞다. 하지만 "OOM 원인을 해결했다"고 쓰면 첫 꼬리질문에서 무너진다.

**AI 검증 사례로 연결**: 멘토가 신입에게 필요하다고 한 "AI 결과가 맞는지 확인하는 기본기"의 사례로 쓸 수 있다. 배치 처리로 해결된 것은 맞지만, 왜 해결됐는지 직접 확인한 과정이 검증이다.

기존 기록(`docs/failure_analysis.md`, `docs/resource_guard.md`, `docs/handoff_duckdb_agent.md`, `docs/measurements.md`)과 대조해서 이미 확인한 것과 아직 가설인 것을 나눈다.

### 2.2 "왜 DuckDB인가, 다른 DB는?"

- 단계 8(Spark 필요성 실측)에서 DuckDB와 Spark를 비교한 기록이 답의 재료다.
- 답은 세 단계로 정리한다.
  1. 한 대에서 처리되는 규모였다 (실측 크기와 행 수)
  2. 이 규모에서는 실측해 보니 Spark 실행 비용이 더 컸다 (`docs/measurements.md` 수치)
  3. 규모가 커지면 무엇으로 가는지
- 현업에서 DuckDB를 많이 쓰지 않는다는 걸 알고 골랐다는 점이 보여야 한다.

### 2.3 플랫폼 방향으로 다시 서술하기

- 멘토는 이 프로젝트를 "원천 가공 파이프라인"으로 봤다. 고도화에서 만든 부분 중 플랫폼에 해당하는 재료가 서류에서 약하게 보였을 가능성이 있다.
- 플랫폼에 해당하는 재료
  - 컬럼 단위 리니지: 분석가가 "이 컬럼은 어디서 왔고, 원천이 바뀌면 무엇이 깨지는지" 직접 확인
  - 리니지 MCP 서버: 분석가나 에이전트가 리니지를 조회하는 통로
  - 데이터 계약(`docs/data_contract.md`): 받는 쪽이 믿고 쓸 수 있는 약속
  - SQL 1차 대응 에이전트: 원천이 바뀌어도 쓰는 쪽 쿼리를 빠르게 복구
- 서술의 주어를 "내가 처리한 데이터"에서 "이걸 쓰는 사람이 덜 하게 된 일"로 바꾼다.

### 2.4 모르는 질문 대처 연습

- "여기까지는 확인했다 / 여기부터는 가설이다 / 이렇게 확인하겠다" 세 칸으로 답한다.
- 2.1의 표가 그대로 연습 재료다.

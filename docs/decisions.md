## 결정 2. 전월세 거래를 행정동에 잇는 방식
- 상황: 전월세 실거래가(오피스텔, 연립다세대)는 위치로 시군구 코드(행정안전부식, 강남구 11680), 법정동 이름(umdNm), 지번(jibun)만 준다. 동네 비교의 기준은 통계청 행정동(SGIS 경계 ADM_CD, 생활이동 코드, 강남구 11230)이다. 한 법정동이 여러 행정동에 걸치는 경우가 있다(예: 역삼동과 역삼1동·역삼2동).
- 선택지:
  - A. 코드 사슬 (법정동 이름 → 법정동 코드 → 행정안전부 행정동 → 통계청 행정동). 장점: 외부 API 불필요, 공식 자료. 단점: 고리가 길어 어긋날 지점이 많고, 법정동이 여러 행정동에 걸치면 거래를 어느 행정동에 넣을지 정할 수 없다.
  - B. 지번 주소 → 좌표(지오코딩) → 행정동 경계와 공간 조인. 장점: 거래마다 정확한 행정동이 나오고 1:N 문제가 없다. 단점: 외부 API 의존, 호출량 제한, 인증키 추가.
  - C. 법정동 경계와 행정동 경계의 겹친 면적 비율로 배분. 장점: API 불필요. 단점: 거래가 법정동 안에 고르게 퍼져 있다고 가정하므로 동네 평균 월세 같은 값이 왜곡된다.
- 결정과 이유: B. 질문의 답이 행정동 단위 비교라서 거래 한 건이 정확히 어느 행정동에 속하는지가 결과를 좌우한다. 지번 주소는 건물 단위라 종류가 거래 수보다 적고, 한 번 얻은 좌표는 저장해 다시 쓸 수 있어 호출량 부담이 줄어든다. A는 B가 실패한 주소의 보조 수단으로만 검토한다.
- 검증: (지오코딩 API를 정하고 샘플을 돌린 뒤 적는다. 예: 2026-10-21 수집분 강남구 오피스텔·연립다세대 고유 지번 수, 좌표 변환 성공률, 실패 사례)
- 결과와 남은 것: 지오코딩 API 선택(결정 3), 실패 주소 처리 방식, 좌표 캐시를 어디에 저장할지(레이크인지 웨어하우스인지)를 정해야 한다.

## 결정 3. 지오코딩 API (결정 5로 대체됨)
- 상황: 결정 2(지번 주소 → 좌표 → 행정동 공간 조인)를 위해 지번 주소를 좌표로 바꿀 API가 필요하다. 2026-10-21 수집분 강남구 전월세 997건의 고유 (구, 법정동, 지번)은 607개다.
- 선택지:
  - A. 브이월드 지오코더 API. 장점: 공공 서비스, 지번 주소 검색 지원, 결과 좌표계 지정 가능성. 단점: 인증 절차와 호출 한도 확인 필요.
  - B. 행정안전부 도로명주소 검색 API + 좌표제공 API. 장점: 공식 주소 체계, 법정동·행정동 정보 동반 가능. 단점: 주소 검색과 좌표 조회가 두 번 호출일 수 있고 키가 여러 개일 수 있음.
  - C. 카카오 로컬 API. 장점: 문서가 잘 되어 있고 지번 인식이 관대함, 행정동 정보 동반 가능. 단점: 민간 서비스, 개발자 계정과 앱 등록 필요, 결과 저장 허용 여부 확인 필요.

- 결과와 남은 것:

## 결정 5. 지번 좌표를 얻는 방법 (결정 3 대체)
- 상황: 결정 2(지번 → 좌표 → 행정동 공간 조인)는 그대로 유지한다. 결정 3에서 고른 카카오 로컬 API는 결과 저장이 금지되어(실시간 호출만 허용) 좌표를 저장해 재사용하는 구조에 쓸 수 없다.
- 선택지:
  - A. 공공 주소·좌표 파일로 로컬 조인. 행정안전부 주소 데이터 중 건물 좌표가 든 파일(법정동 코드 + 지번 + 좌표)을 받아 전월세 (법정동, 지번)과 DB 안에서 조인. 장점: API 호출 없음, 공공 데이터라 저장 제약이 덜할 가능성, 좌표가 UTM-K이면 경계와 바로 맞음. 단점: 파일이 크고, 법정동 이름 → 코드 변환과 지번 표기 맞추기가 필요. 어떤 파일에 무엇이 있는지 아직 확인하지 않음.
  - B. 다른 지오코딩 API(브이월드, 행정안전부 좌표제공 API). 장점: 지금 설계를 거의 그대로 씀. 단점: 저장 허용 여부를 다시 확인해야 하고 호출 한도 문제는 그대로.
  - C. 코드 사슬(결정 2의 A). 장점: 외부 의존 없음. 단점: 한 법정동이 여러 행정동에 걸치는 문제가 다시 생김.
- 결정과 이유: A. 결정 2의 장점(거래마다 정확한 행정동)을 살리면서 외부 API 의존과 약관 문제를 함께 없앤다.
- 검증: 2026-10-21. 상가정보의 지번코드가 필지 고유번호(PNU) 구조임을 확인했고(554,069 / 554,092행), 전월세 지번으로 PNU를 만들 수 있었다. 상가정보만으로는 607개 중 199개(33%)만 좌표가 있었고, 연속지적도 서울(896,692 필지)에서는 **607 / 607** 모두 찾았다(measurements.md 측정 4).
- 결과와 남은 것:
  - 좌표 출처는 연속지적도(필지 폴리곤)로 한다. 좌표계가 EPSG:5186이라 SGIS 경계(EPSG:5179)와 맞추려면 변환한다.
  - **연속지적도의 이용허락조건을 아직 확인하지 않았다.** 결정 3의 교훈대로 단계 5 적재 전에 확인한다.
  - 법정동 이름 → 법정동 코드 대응을 상가정보에서 만들었으므로, 상가가 없는 법정동을 위한 공식 코드표가 필요한지 확인한다.
  - 필지 대표점(무게중심 또는 내부 대표점)을 단계 5에서 정한다.

- 선택지:
  - A. API. 장점: 자동으로 받을 수 있어 단계 7 Airflow에 그대로 연결된다. 형식이 일정하다. 단점: 2분기 전 데이터이고 언제 갱신될지 모른다.
  - B. 최신 분기 파일(손으로 받음). 장점: 최신 데이터. 단점: 분기마다 사람이 받아야 하고, 형식이 바뀐 이력이 있어 정제가 두 형식을 읽어야 한다. (Airflow는 레이크에 새 파일이 들어왔는지 확인하는 방식으로 연결할 수 있다.)
  - C. 둘 다 받고 기준일이 가장 최근인 것을 사용. 장점: 사람이 넣으면 최신, 안 넣어도 값이 있음. 단점: API 데이터의 기준일을 알아낼 방법이 필요하고 정제가 복잡해진다.
- 결정과 이유: A. 단계 7의 Airflow 연동까지 생각해 자동 수집을 우선한다. (사용자 선택)
- 검증: 2026-10-21 ingestion/seoul_api.py congestion 실행, list_total_count 1,671, 2쪽. 20251130.csv와 1,671행 일치.

  - API 내용이 바뀌는 시점을 알아챌 수 있어야 한다. 수집할 때마다 이전 수집분과 내용이 같은지 비교해, 바뀌면 알리는 검사를 단계 4 또는 7에서 둔다.
  - API가 계속 갱신되지 않아 질문의 답에 영향이 크다고 판단되면 B나 C를 다시 검토한다.
## 결정 8. 정제를 어디서 할까
- 상황: 단계 4에서 전월세 정제·검증 규칙(docs/rules.md 1절)을 합의했다. 원본 형식이 XML, CSV(CP949, UTF-8), xlsx, zip 안의 CSV, shp로 제각각이고, 단계 5의 공간 조인은 PostgreSQL(PostGIS)에서 한다.
- 선택지:
  - A. Python으로 정제·검증 → PostgreSQL의 스테이징 테이블(통과)과 격리 테이블(사유 포함)에 적재. 장점: 형식이 다른 원본을 다루기 쉽고, 규칙 하나가 함수 하나라 시험하기 쉽고, 결과가 바로 PostGIS 공간 조인으로 이어진다. 단점: DB 연결 라이브러리(psycopg) 추가.
  - B. 원본을 문자열 그대로 DB에 넣고 SQL로 정제(ELT). 장점: 정제 규칙이 DB 안에서 다 보이고 실무에서 흔한 방식. 단점: 원본을 푸는 Python 코드는 어차피 필요하고, 레이크와 같은 내용의 원본 테이블이 하나 더 생긴다.
  - C. Python으로 정제 → Parquet 파일. 장점: DB 없이 확인 가능. 단점: 단계 5에서 결국 DB에 다시 넣어야 해서 이유를 대기 어려운 중간 단계가 된다.
- 결정과 이유: A. 레이크가 이미 원본 보관 역할을 하므로 원본을 DB에 한 번 더 넣을 이유가 약하고, 어차피 Python이 원본을 읽어야 하니 읽는 김에 정제·검증까지 하는 것이 단계가 가장 적다. psycopg는 "Python에서 PostgreSQL에 쓰기"라는 분명한 이유가 있다.

## 결정 16. 폴리곤의 대표점
- 상황: 전월세는 필지(폴리곤)를 점 하나로 줄여 행정동에 붙이고, "행정동 중심에서 가장 가까운 역"은 행정동(폴리곤)을 점 하나로 줄여 찾는다.
- 선택지:
  - A. 무게중심(ST_Centroid). 장점: 흔하고 직관적이다. 단점: 오목한 도형은 무게중심이 도형 밖에 떨어질 수 있어, 필지 점이 옆 동에 떨어지면 거래가 엉뚱한 동에 붙는다.
  - B. 도형 안의 대표점(ST_PointOnSurface). 장점: 항상 도형 안쪽이라 필지 → 행정동이 틀리지 않는다. 단점: 도형의 가운데가 아닐 수 있고 길쭉한 도형에서는 한쪽에 치우칠 수 있다.
- 결정과 이유: 필지와 행정동 모두 B (2026-10-21 사용자 결정). 필지는 점이 그 필지 안에 있는 것이 정확성의 전부이고, 행정동도 무게중심이 동 밖에 떨어지면 다른 동의 역이 잡힐 수 있다.
- 검증: 2026-10-21. 서울 426개 동 중 무게중심이 동 밖에 떨어지는 동이 **4개**다. 무게중심과 도형 안 대표점으로 각각 가장 가까운 역을 찾으면 **46개 동**에서 다른 역이 나온다. 필지 896,692개의 대표점 중 경계 밖에 떨어진 것은 19개(dong_id NULL).
- 결과와 남은 것: 46개 동은 기준점에 따라 "가장 가까운 역"이 바뀐다. 단계 9에서 이 동들의 결과를 눈으로 확인한다. 경계 밖 필지 19개가 전월세 거래에 쓰이는지 단계 9에서 본다(지금 강남 1,032건은 모두 행정동이 정해졌다).

## 결정 18. 전월세의 "바뀐 것만 반영"과 중복 판별 키
- 상황: 전월세 실거래가는 신고 지연 때문에 같은 계약월을 다시 받으면 건수가 늘어난다(측정 1: 같은 날 02시대 238 → 14시 243). 동·호가 없어 거래 고유 키가 없다. 지금 wh.fact_rent 뷰는 같은 (출처, 구, 계약년월)이면 가장 최근 수집분만 본다.
- 선택지:
  - A. 스냅샷 교체(지금 방식). 같은 달은 가장 최근 수집분 전체로 바꾼다. 장점: 가장 단순하고, 같은 거래를 두 번 세지 않고, 취소되어 사라진 거래도 자동으로 빠진다. 단점: 두 수집 사이에 무엇이 새로 들어왔고 사라졌는지 알 수 없다.
  - B. 거래 지문 + 병합. 거래마다 "모든 칸 + 같은 값 안에서의 순번"으로 지문을 만들어 새 지문은 추가, 사라진 지문은 표시. 장점: 신고 지연을 거래 단위로 잴 수 있다. 단점: 완전히 같은 거래 두 건은 순번으로만 구분되어 흔들릴 수 있고, 구현이 크다.
  - C. 적재는 A, 지문은 측정에만. 장점: 적재는 단순하고 신고 지연 측정은 정밀하다. 단점: 지문이 적재 규칙이 아니라 측정 도구로만 남는다.
- 결정과 이유: C (2026-10-21 사용자 결정). 받는 쪽(부동산 플랫폼)에 주는 것은 지금 시점의 동네 시세라서 가장 최근 스냅샷이면 충분하다. 몇 달 전까지 다시 받을지를 정하려면 거래 단위의 변화가 필요하므로 지문은 측정에 쓴다. CLAUDE.md 단계 6의 "중복 판별 키"는 **적재에는 필요 없고(스냅샷 교체), 측정에는 지문(모든 칸 + 같은 값 안에서의 순번)을 쓴다**로 정한다.
- 검증: 2026-10-30, `measure/rent_fingerprint.py`로 10-21과 10-28 레이크를 비교(측정 1). 202607~202609 일주일 사이 추가 717, 사라짐 37. 사라진 37건 중 26건은 건물 이름만 정정되어 다시 나타났고 11건은 다시 나타나지 않았다. 스냅샷 교체에서는 모두 다음 수집에서 반영된다. 행을 이어 붙였다면 이 37건이 중복이나 유령 거래로 남았다.
- 결과와 남은 것: 다시 받을 개월 수(N)는 10-28 측정으로 정한다. 단계 7 DAG에서 N은 설정값 하나로 둔다.

## 결정 19. Airflow 실행 방식
- 상황: Airflow는 Windows에서 직접 실행할 수 없어 Docker가 필요하다. 수집·정제 스크립트가 Airflow 컨테이너 안에서 돌아야 하므로 requirements.txt의 라이브러리와 프로젝트 폴더, lake/가 컨테이너에 있어야 한다. 컨테이너 안에서 DB 주소는 db:5432다.
- 선택지:
  - A. 공식 docker-compose 그대로(CeleryExecutor, Redis, 작업자, 별도 메타 DB 등 6~7개 컨테이너). 장점: 문서와 같다. 단점: 이 규모(출처 몇 개, 하루 몇 번)에 과하고 부품이 많다.
  - B. 최소 구성을 지금 compose에 추가: Airflow 컨테이너 하나(LocalExecutor), 메타 정보는 지금 DB 서버에 airflow라는 DB를 따로 만들어 저장. 장점: 컨테이너 하나만 늘고 이해할 부품이 적다. 단점: 데이터 DB와 메타 DB가 같은 서버라 한쪽이 무거우면 영향을 준다.
  - C. B + 메타 DB 전용 Postgres 컨테이너. 장점: 완전히 분리된다. 단점: 컨테이너가 둘 는다.
- 결정과 이유: B (2026-10-21 사용자 결정). DAG가 하루 몇 번, 몇 분짜리라 메타 DB 부하가 작고, 서버는 같아도 DB는 seoul과 airflow로 나뉘어 테이블이 섞이지 않는다.
- 검증: 2026-10-21. docker-compose.yml에 airflow 서비스(seoul-airflow:3.3.2, command standalone, LocalExecutor)와 db healthcheck(pg_isready)를 더했다. db가 healthy가 된 뒤 airflow가 켜지고 scheduler, triggerer, dag-processor, API 서버가 모두 시작됐다. http://localhost:8080 응답 200, /api/v2/version = 3.3.2. 메타 DB는 같은 서버의 airflow DB(warehouse/sql/00_airflow_db.sql). 로그인 없이 개발용 관리자(SIMPLE_AUTH_MANAGER_ALL_ADMINS)로 접속되고, 포트는 127.0.0.1에만 열었다. 메모리(docker stats, 1회): airflow 약 1.17GiB, db 약 51MiB.
- 결과와 남은 것: 메타 DB 부하가 실제로 보이면 C로 옮긴다. 실행기 작업자가 기본값 32개로 뜬다. 줄이려면 AIRFLOW__CORE__PARALLELISM.

## 결정 21. 전월세 DAG의 범위, 일정, 재시도
- 상황: 전월세는 신고 지연 때문에 최근 몇 달을 다시 받아야 한다(결정 18, 개월 수 N은 10-28 측정 후). 질문과 받는 쪽(부동산 플랫폼)은 서울 전체 동네를 본다. 지금까지는 강남구만 받았다.
- 선택지:
  - 대상 구: A. 강남구만(호출이 적다, 서울 전체 비교에는 부족) / B. 서울 25개 구(질문에 맞다, 호출 25배. 25개 구 × 2개 출처 × N개월, N=3이면 한 번에 150회로 개발 계정 하루 10,000회 안).
  - 일정: A. 매일(하루 사이 변화가 작아 대부분 같은 결과를 다시 받음) / B. 매주 한 번(10-28 측정 주기와 같고 호출이 적다, 최대 일주일 늦게 반영).

- 결정과 이유: A (2026-11-03 사용자 결정). 되돌리는 데 필요한 것이 이미 모두 남아 있다.

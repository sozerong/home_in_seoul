## 결정 2. 전월세 거래를 행정동에 잇는 방식
- 상황: 전월세 실거래가(오피스텔, 연립다세대)는 위치로 시군구 코드(행정안전부식, 강남구 11680), 법정동 이름(umdNm), 지번(jibun)만 준다. 동네 비교의 기준은 통계청 행정동(SGIS 경계 ADM_CD, 생활이동 코드, 강남구 11230)이다. 한 법정동이 여러 행정동에 걸치는 경우가 있다(예: 역삼동과 역삼1동·역삼2동).
- 선택지:
  - A. 코드 사슬 (법정동 이름 → 법정동 코드 → 행정안전부 행정동 → 통계청 행정동). 장점: 외부 API 불필요, 공식 자료. 단점: 고리가 길어 어긋날 지점이 많고, 법정동이 여러 행정동에 걸치면 거래를 어느 행정동에 넣을지 정할 수 없다.
  - B. 지번 주소 → 좌표(지오코딩) → 행정동 경계와 공간 조인. 장점: 거래마다 정확한 행정동이 나오고 1:N 문제가 없다. 단점: 외부 API 의존, 호출량 제한, 인증키 추가.
  - C. 법정동 경계와 행정동 경계의 겹친 면적 비율로 배분. 장점: API 불필요. 단점: 거래가 법정동 안에 고르게 퍼져 있다고 가정하므로 동네 평균 월세 같은 값이 왜곡된다.
- 결정과 이유: B. 질문의 답이 행정동 단위 비교라서 거래 한 건이 정확히 어느 행정동에 속하는지가 결과를 좌우한다. 지번 주소는 건물 단위라 종류가 거래 수보다 적고, 한 번 얻은 좌표는 저장해 다시 쓸 수 있어 호출량 부담이 줄어든다. A는 B가 실패한 주소의 보조 수단으로만 검토한다.
- 검증: (지오코딩 API를 정하고 샘플을 돌린 뒤 적는다. 예: 2026-10-21 수집분 강남구 오피스텔·연립다세대 고유 지번 수, 좌표 변환 성공률, 실패 사례)
- 결과와 남은 것: 지오코딩 API 선택(결정 3), 실패 주소 처리 방식, 좌표 캐시를 어디에 저장할지(레이크인지 웨어하우스인지)를 정해야 한다.

## 결정 3. 지오코딩 API (결정 5로 대체됨)
- 상황: 결정 2(지번 주소 → 좌표 → 행정동 공간 조인)를 위해 지번 주소를 좌표로 바꿀 API가 필요하다. 2026-10-21 수집분 강남구 전월세 997건의 고유 (구, 법정동, 지번)은 607개다.
- 선택지:
  - A. 브이월드 지오코더 API. 장점: 공공 서비스, 지번 주소 검색 지원, 결과 좌표계 지정 가능성. 단점: 인증 절차와 호출 한도 확인 필요.
  - B. 행정안전부 도로명주소 검색 API + 좌표제공 API. 장점: 공식 주소 체계, 법정동·행정동 정보 동반 가능. 단점: 주소 검색과 좌표 조회가 두 번 호출일 수 있고 키가 여러 개일 수 있음.
  - C. 카카오 로컬 API. 장점: 문서가 잘 되어 있고 지번 인식이 관대함, 행정동 정보 동반 가능. 단점: 민간 서비스, 개발자 계정과 앱 등록 필요, 결과 저장 허용 여부 확인 필요.

- 결과와 남은 것:

## 결정 5. 지번 좌표를 얻는 방법 (결정 3 대체)
- 상황: 결정 2(지번 → 좌표 → 행정동 공간 조인)는 그대로 유지한다. 결정 3에서 고른 카카오 로컬 API는 결과 저장이 금지되어(실시간 호출만 허용) 좌표를 저장해 재사용하는 구조에 쓸 수 없다.
- 선택지:
  - A. 공공 주소·좌표 파일로 로컬 조인. 행정안전부 주소 데이터 중 건물 좌표가 든 파일(법정동 코드 + 지번 + 좌표)을 받아 전월세 (법정동, 지번)과 DB 안에서 조인. 장점: API 호출 없음, 공공 데이터라 저장 제약이 덜할 가능성, 좌표가 UTM-K이면 경계와 바로 맞음. 단점: 파일이 크고, 법정동 이름 → 코드 변환과 지번 표기 맞추기가 필요. 어떤 파일에 무엇이 있는지 아직 확인하지 않음.
  - B. 다른 지오코딩 API(브이월드, 행정안전부 좌표제공 API). 장점: 지금 설계를 거의 그대로 씀. 단점: 저장 허용 여부를 다시 확인해야 하고 호출 한도 문제는 그대로.
  - C. 코드 사슬(결정 2의 A). 장점: 외부 의존 없음. 단점: 한 법정동이 여러 행정동에 걸치는 문제가 다시 생김.
- 결정과 이유: A. 결정 2의 장점(거래마다 정확한 행정동)을 살리면서 외부 API 의존과 약관 문제를 함께 없앤다.
- 검증: 2026-10-21. 상가정보의 지번코드가 필지 고유번호(PNU) 구조임을 확인했고(554,069 / 554,092행), 전월세 지번으로 PNU를 만들 수 있었다. 상가정보만으로는 607개 중 199개(33%)만 좌표가 있었고, 연속지적도 서울(896,692 필지)에서는 **607 / 607** 모두 찾았다(measurements.md 측정 4).
- 결과와 남은 것:
  - 좌표 출처는 연속지적도(필지 폴리곤)로 한다. 좌표계가 EPSG:5186이라 SGIS 경계(EPSG:5179)와 맞추려면 변환한다.
  - **연속지적도의 이용허락조건을 아직 확인하지 않았다.** 결정 3의 교훈대로 단계 5 적재 전에 확인한다.
  - 법정동 이름 → 법정동 코드 대응을 상가정보에서 만들었으므로, 상가가 없는 법정동을 위한 공식 코드표가 필요한지 확인한다.
  - 필지 대표점(무게중심 또는 내부 대표점)을 단계 5에서 정한다.

- 선택지:
  - A. API. 장점: 자동으로 받을 수 있어 단계 7 Airflow에 그대로 연결된다. 형식이 일정하다. 단점: 2분기 전 데이터이고 언제 갱신될지 모른다.
  - B. 최신 분기 파일(손으로 받음). 장점: 최신 데이터. 단점: 분기마다 사람이 받아야 하고, 형식이 바뀐 이력이 있어 정제가 두 형식을 읽어야 한다. (Airflow는 레이크에 새 파일이 들어왔는지 확인하는 방식으로 연결할 수 있다.)
  - C. 둘 다 받고 기준일이 가장 최근인 것을 사용. 장점: 사람이 넣으면 최신, 안 넣어도 값이 있음. 단점: API 데이터의 기준일을 알아낼 방법이 필요하고 정제가 복잡해진다.
- 결정과 이유: A. 단계 7의 Airflow 연동까지 생각해 자동 수집을 우선한다. (사용자 선택)
- 검증: 2026-10-21 ingestion/seoul_api.py congestion 실행, list_total_count 1,671, 2쪽. 20251130.csv와 1,671행 일치.

  - API 내용이 바뀌는 시점을 알아챌 수 있어야 한다. 수집할 때마다 이전 수집분과 내용이 같은지 비교해, 바뀌면 알리는 검사를 단계 4 또는 7에서 둔다.
  - API가 계속 갱신되지 않아 질문의 답에 영향이 크다고 판단되면 B나 C를 다시 검토한다.
## 결정 8. 정제를 어디서 할까
- 상황: 단계 4에서 전월세 정제·검증 규칙(docs/rules.md 1절)을 합의했다. 원본 형식이 XML, CSV(CP949, UTF-8), xlsx, zip 안의 CSV, shp로 제각각이고, 단계 5의 공간 조인은 PostgreSQL(PostGIS)에서 한다.
- 선택지:
  - A. Python으로 정제·검증 → PostgreSQL의 스테이징 테이블(통과)과 격리 테이블(사유 포함)에 적재. 장점: 형식이 다른 원본을 다루기 쉽고, 규칙 하나가 함수 하나라 시험하기 쉽고, 결과가 바로 PostGIS 공간 조인으로 이어진다. 단점: DB 연결 라이브러리(psycopg) 추가.
  - B. 원본을 문자열 그대로 DB에 넣고 SQL로 정제(ELT). 장점: 정제 규칙이 DB 안에서 다 보이고 실무에서 흔한 방식. 단점: 원본을 푸는 Python 코드는 어차피 필요하고, 레이크와 같은 내용의 원본 테이블이 하나 더 생긴다.
  - C. Python으로 정제 → Parquet 파일. 장점: DB 없이 확인 가능. 단점: 단계 5에서 결국 DB에 다시 넣어야 해서 이유를 대기 어려운 중간 단계가 된다.
- 결정과 이유: A. 레이크가 이미 원본 보관 역할을 하므로 원본을 DB에 한 번 더 넣을 이유가 약하고, 어차피 Python이 원본을 읽어야 하니 읽는 김에 정제·검증까지 하는 것이 단계가 가장 적다. psycopg는 "Python에서 PostgreSQL에 쓰기"라는 분명한 이유가 있다.

## 결정 16. 폴리곤의 대표점
- 상황: 전월세는 필지(폴리곤)를 점 하나로 줄여 행정동에 붙이고, "행정동 중심에서 가장 가까운 역"은 행정동(폴리곤)을 점 하나로 줄여 찾는다.
- 선택지:
  - A. 무게중심(ST_Centroid). 장점: 흔하고 직관적이다. 단점: 오목한 도형은 무게중심이 도형 밖에 떨어질 수 있어, 필지 점이 옆 동에 떨어지면 거래가 엉뚱한 동에 붙는다.
  - B. 도형 안의 대표점(ST_PointOnSurface). 장점: 항상 도형 안쪽이라 필지 → 행정동이 틀리지 않는다. 단점: 도형의 가운데가 아닐 수 있고 길쭉한 도형에서는 한쪽에 치우칠 수 있다.
- 결정과 이유: 필지와 행정동 모두 B (2026-10-21 사용자 결정). 필지는 점이 그 필지 안에 있는 것이 정확성의 전부이고, 행정동도 무게중심이 동 밖에 떨어지면 다른 동의 역이 잡힐 수 있다.
- 검증: 2026-10-21. 서울 426개 동 중 무게중심이 동 밖에 떨어지는 동이 **4개**다. 무게중심과 도형 안 대표점으로 각각 가장 가까운 역을 찾으면 **46개 동**에서 다른 역이 나온다. 필지 896,692개의 대표점 중 경계 밖에 떨어진 것은 19개(dong_id NULL).
- 결과와 남은 것: 46개 동은 기준점에 따라 "가장 가까운 역"이 바뀐다. 단계 9에서 이 동들의 결과를 눈으로 확인한다. 경계 밖 필지 19개가 전월세 거래에 쓰이는지 단계 9에서 본다(지금 강남 1,032건은 모두 행정동이 정해졌다).

## 결정 18. 전월세의 "바뀐 것만 반영"과 중복 판별 키
- 상황: 전월세 실거래가는 신고 지연 때문에 같은 계약월을 다시 받으면 건수가 늘어난다(측정 1: 같은 날 02시대 238 → 14시 243). 동·호가 없어 거래 고유 키가 없다. 지금 wh.fact_rent 뷰는 같은 (출처, 구, 계약년월)이면 가장 최근 수집분만 본다.
- 선택지:
  - A. 스냅샷 교체(지금 방식). 같은 달은 가장 최근 수집분 전체로 바꾼다. 장점: 가장 단순하고, 같은 거래를 두 번 세지 않고, 취소되어 사라진 거래도 자동으로 빠진다. 단점: 두 수집 사이에 무엇이 새로 들어왔고 사라졌는지 알 수 없다.
  - B. 거래 지문 + 병합. 거래마다 "모든 칸 + 같은 값 안에서의 순번"으로 지문을 만들어 새 지문은 추가, 사라진 지문은 표시. 장점: 신고 지연을 거래 단위로 잴 수 있다. 단점: 완전히 같은 거래 두 건은 순번으로만 구분되어 흔들릴 수 있고, 구현이 크다.
  - C. 적재는 A, 지문은 측정에만. 장점: 적재는 단순하고 신고 지연 측정은 정밀하다. 단점: 지문이 적재 규칙이 아니라 측정 도구로만 남는다.
- 결정과 이유: C (2026-10-21 사용자 결정). 받는 쪽(부동산 플랫폼)에 주는 것은 지금 시점의 동네 시세라서 가장 최근 스냅샷이면 충분하다. 몇 달 전까지 다시 받을지를 정하려면 거래 단위의 변화가 필요하므로 지문은 측정에 쓴다. CLAUDE.md 단계 6의 "중복 판별 키"는 **적재에는 필요 없고(스냅샷 교체), 측정에는 지문(모든 칸 + 같은 값 안에서의 순번)을 쓴다**로 정한다.
- 검증: 2026-10-30, `measure/rent_fingerprint.py`로 10-21과 10-28 레이크를 비교(측정 1). 202607~202609 일주일 사이 추가 717, 사라짐 37. 사라진 37건 중 26건은 건물 이름만 정정되어 다시 나타났고 11건은 다시 나타나지 않았다. 스냅샷 교체에서는 모두 다음 수집에서 반영된다. 행을 이어 붙였다면 이 37건이 중복이나 유령 거래로 남았다.
- 결과와 남은 것: 다시 받을 개월 수(N)는 10-28 측정으로 정한다. 단계 7 DAG에서 N은 설정값 하나로 둔다.

## 결정 19. Airflow 실행 방식
- 상황: Airflow는 Windows에서 직접 실행할 수 없어 Docker가 필요하다. 수집·정제 스크립트가 Airflow 컨테이너 안에서 돌아야 하므로 requirements.txt의 라이브러리와 프로젝트 폴더, lake/가 컨테이너에 있어야 한다. 컨테이너 안에서 DB 주소는 db:5432다.
- 선택지:
  - A. 공식 docker-compose 그대로(CeleryExecutor, Redis, 작업자, 별도 메타 DB 등 6~7개 컨테이너). 장점: 문서와 같다. 단점: 이 규모(출처 몇 개, 하루 몇 번)에 과하고 부품이 많다.
  - B. 최소 구성을 지금 compose에 추가: Airflow 컨테이너 하나(LocalExecutor), 메타 정보는 지금 DB 서버에 airflow라는 DB를 따로 만들어 저장. 장점: 컨테이너 하나만 늘고 이해할 부품이 적다. 단점: 데이터 DB와 메타 DB가 같은 서버라 한쪽이 무거우면 영향을 준다.
  - C. B + 메타 DB 전용 Postgres 컨테이너. 장점: 완전히 분리된다. 단점: 컨테이너가 둘 는다.
- 결정과 이유: B (2026-10-21 사용자 결정). DAG가 하루 몇 번, 몇 분짜리라 메타 DB 부하가 작고, 서버는 같아도 DB는 seoul과 airflow로 나뉘어 테이블이 섞이지 않는다.
- 검증: 2026-10-21. docker-compose.yml에 airflow 서비스(seoul-airflow:3.3.2, command standalone, LocalExecutor)와 db healthcheck(pg_isready)를 더했다. db가 healthy가 된 뒤 airflow가 켜지고 scheduler, triggerer, dag-processor, API 서버가 모두 시작됐다. http://localhost:8080 응답 200, /api/v2/version = 3.3.2. 메타 DB는 같은 서버의 airflow DB(warehouse/sql/00_airflow_db.sql). 로그인 없이 개발용 관리자(SIMPLE_AUTH_MANAGER_ALL_ADMINS)로 접속되고, 포트는 127.0.0.1에만 열었다. 메모리(docker stats, 1회): airflow 약 1.17GiB, db 약 51MiB.
- 결과와 남은 것: 메타 DB 부하가 실제로 보이면 C로 옮긴다. 실행기 작업자가 기본값 32개로 뜬다. 줄이려면 AIRFLOW__CORE__PARALLELISM.

## 결정 21. 전월세 DAG의 범위, 일정, 재시도
- 상황: 전월세는 신고 지연 때문에 최근 몇 달을 다시 받아야 한다(결정 18, 개월 수 N은 10-28 측정 후). 질문과 받는 쪽(부동산 플랫폼)은 서울 전체 동네를 본다. 지금까지는 강남구만 받았다.
- 선택지:
  - 대상 구: A. 강남구만(호출이 적다, 서울 전체 비교에는 부족) / B. 서울 25개 구(질문에 맞다, 호출 25배. 25개 구 × 2개 출처 × N개월, N=3이면 한 번에 150회로 개발 계정 하루 10,000회 안).
  - 일정: A. 매일(하루 사이 변화가 작아 대부분 같은 결과를 다시 받음) / B. 매주 한 번(10-28 측정 주기와 같고 호출이 적다, 최대 일주일 늦게 반영).

## 결정 40. 리니지 단위: 컬럼 (변경에 강한 파이프라인 P4)
- 상황: 원천 데이터나 요구사항이 바뀌면 어디까지 영향이 가는지 지금은 사람 기억과 검색으로 찾는다(측정 13: `DPTRE_STTN` 검색으로 코드 1, 시험 1, 문서 3개). 출처, 모델, 컬럼 수가 늘수록 더 어려워진다. 그래서 데이터 사이 관계의 지도(리니지)를 만든다. 먼저 지도의 단위를 정한다.
- 선택지:
  - A. 테이블 리니지. 장점: 이미 있다. `target/manifest.json`에 dbt 모델 17개의 `depends_on`이 있고, 원천 → stg는 정제 파일 하나당 표 하나라 자명하다. 비용이 거의 없고 틀릴 일도 적다. 단점: 컬럼 하나가 바뀌어도 그 표를 쓰는 하류 표 전체가 후보가 되어, 표 안을 사람이 다시 열어 봐야 한다. 표 이름이 그대로인 변화(원천 필드 개명, S1)는 지도에 보이지 않는다. 요구사항이 바뀔 때 어느 원천 컬럼부터 어느 상품 컬럼까지 손댈지 답하지 못한다.
  - B. 컬럼 리니지. 장점: 변화가 일어나는 단위(컬럼)와 답의 단위가 같다. 영향이 없는 곳도 보여 "유지되는 부분"을 데이터로 보일 수 있다. 하류(원천이 바뀌면 무엇이 깨지나)와 상류(이 상품 컬럼을 만들려면 어느 원천이 필요한가)로 모두 따라갈 수 있다. 표 단위로 묶으면 테이블 리니지도 나온다. 단점: 새로 만들어야 하고, 틀린 지도는 없는 것보다 위험해 정확성 확인과 갱신이 필요하다.
- 결정과 이유: B (2026-11-12 사용자 결정). 테이블 단위로 하면 그 안에서 컬럼을 다시 찾는 작업이 한 번 더 남으므로, 처음부터 컬럼 단위로 그린다.
- 검증: (구현 후) S4에서 테이블 리니지가 올린 후보 수와 컬럼 리니지가 낸 영향 컬럼 수를 비교한다.
- 결과와 남은 것: 추출 방식은 결정 41.

## 결정 41. 리니지 추출 방식: 코드(SQL) 파싱 (변경에 강한 파이프라인 P4)
- 상황: 결정 40에 따라 컬럼 리니지를 뽑을 방법을 정한다. 검토 기준은 (1) 컬럼 단위로 정확할 것, (2) 바꾸기 전에 미리 볼 수 있을 것(목적이 변경 영향을 미리 아는 것), (3) 원천부터 상품까지 이어질 것, (4) 추가 운영 부담이 작을 것(PC 한 대, CLAUDE.md 4절 6번). 변환은 두 구간에 나뉘어 있다: 원천 → stg는 Python 정제(`transform/*.py`), stg → wh → mart → 상품은 dbt SQL. 참고한 사례: 당근 컬럼 레벨 리니지 구축기(BigQuery 쿼리 로그를 파싱하는 방식을 택함).
- 선택지:
  - 1. DB 메타데이터(`information_schema.view_column_usage`, `pg_depend`, dbt `manifest.json`). 장점: 추가 비용 0. 단점: 의존 관계가 뷰에만 남는다. dbt 모델 17개 중 뷰는 3개(fact_commute, fact_congestion, fact_rent)이고 나머지 14개는 `CREATE TABLE AS`로 만든 테이블이라 기록이 없다. 뷰도 "어떤 컬럼을 썼다"까지만 남고 결과 컬럼과의 대응은 없다. manifest는 테이블 단위다.
  - 2. OpenLineage(실행할 때 이벤트 수집). 장점: 표준 스펙, 실제 실행 경로를 기록한다. 실행 경로가 Airflow 하나라 계측할 곳은 적다. 단점: dbt와 정제를 BashOperator로 실행해 컬럼 정보가 나오지 않는다. dbt용 래퍼가 이 버전에서 동작하는지 [확인 필요]. 이벤트를 받을 서버가 하나 더 필요하다. 실행한 뒤에만 지도가 생겨 기준 (2)에 맞지 않는다.
  - 3. DB 쿼리 로그 파싱. 장점: 실제로 실행된 SQL을 모두 본다. 단점: 지금 PostgreSQL 쿼리 로그가 꺼져 있다. 정제 적재가 `INSERT ... VALUES`(`executemany`)라 로그에 원천 필드 이름이 없어 원천 → stg 구간을 이을 수 없다. 실행 뒤에만 생기고 pgAdmin에서 손으로 던진 쿼리가 섞인다. 당근은 쿼리가 여러 조직과 경로에서 제출되어 모이는 곳이 로그뿐이었지만, 여기는 변환 SQL이 레포 한 곳(`warehouse/dbt/models`)에 모여 있다.
  - 4. 코드 파싱(dbt가 컴파일한 SQL). 장점: 입력이 이미 있다(`target/compiled/`의 SQL 17개, `manifest.json`, stg 컬럼이 적힌 DDL `warehouse/sql/01~06`). 실행 없이 코드만으로 지도가 나와 바꾸기 전에 볼 수 있다. 단점: 파서 의존성이 하나 는다. 컴파일된 SQL이 빌드 스키마(`wh_build`, `mart_build`)를 가리켜 실제 이름으로 바꾸는 처리가 필요하다. Python 정제 구간은 보지 못한다.
  - 5. Python 정제 구간을 위한 방법. 5a: 원천 필드 → stg 컬럼 대응을 파일로 선언(P1 소스 계약과 겸용, 정제 코드가 그 파일을 읽으면 어긋나지 않음). 5b: 이름 대응과 정제를 SQL로 옮겨 4 하나로 전 구간을 덮음(정제 구조를 크게 바꿈).
- 결정과 이유: 4 (2026-11-12 사용자 결정). 1, 2, 3은 위 단점으로 제외한다. 결론은 당근과 같은 SQL 파싱이지만 입력이 다르다: 당근은 쿼리가 흩어져 있어 로그를 택했고, 여기는 변환이 코드 한 곳에 모여 있어 코드를 택했다. Python 구간은 5b 방향으로 검토하고, 정제를 Python과 SQL 중 어디에 둘지는 다음 결정에서 정한다.
- 검증: 1의 "뷰 3개"는 dbt 설정(`dbt_project.yml`의 `+materialized: table`, 모델 파일 3개의 view 설정)에서 확인했다. DB 카탈로그를 직접 조회하지는 않았다 [미측정].
- 결과와 남은 것: 파서 선택, 결과 저장 형식, 정확성 확인 방법은 정제 위치를 정한 뒤 정한다.

## 결정 42. 정제 위치: 파싱만 Python, 정제는 SQL(dbt) (변경에 강한 파이프라인)
- 상황: 결정 41에서 리니지를 코드(SQL) 파싱으로 뽑기로 했다. 지금은 원천 → stg 구간의 이름 대응, 정제, 검증, 격리가 모두 Python(`transform/*.py`)에 있어 SQL 파싱으로 이 구간을 볼 수 없다. 이 구간을 어디에 둘지 정한다.
- 선택지:
  - A. 지금처럼 Python에서 정제(ETL). 장점: 정상 동작하고 시험이 있어 옮기는 비용이 0이다. XML 파싱, 좌표 판별, 코드표 생성처럼 한 행씩 다루는 일에 자연스럽다. 리니지는 선언(결정 41의 5a, P1 소스 계약과 겸용)으로 잇는다. 단점: 원천이 바뀌어도 규칙이 바뀌어도 같은 Python 파일을 고친다. 리니지가 두 방식(파싱과 선언)으로 나뉜다.
  - B. 파싱만 Python, 이름 대응·정제·검증·격리는 SQL(dbt)(ELT). Python은 파일을 읽어 원천 이름 그대로 원본 표에 넣기만 한다. 장점: 받는 부분(파싱)과 꺼내는 부분(SQL)이 갈라져, 원천이 바뀌면 받는 쪽만, 요구사항이 바뀌면 SQL만 고친다. 원본을 jsonb로 담으면 새 필드가 적재를 실패시키지 않는다(S2). 이름 대응이 SQL 한 곳에 있어 파서가 리니지로 읽는다(S1). 규칙을 고치면 그 모델만 다시 빌드하고 레이크는 다시 읽지 않는다(S3). 이미 있는 것: 격리 표가 원본을 jsonb `raw`로 담고 있다, dbt `sources.yml`의 출처 7개, 테스트 65개, blue/green 교체(결정 30, 32). 정제 모델의 출력 이름을 지금 stg와 같게 하면 wh·mart·상품은 고치지 않는다(측정 13에서 stg 이후 고칠 곳 0). 단점: 정제 모듈 6개, 시험 7개, `docs/rules.md` 규칙을 옮기고 출처마다 결과가 같음을 증명해야 한다. 처리 단위 멱등을 dbt로 다시 구현해야 한다(incremental delete+insert [확인 필요]). 생활이동은 Spark·Iceberg 경로라 예외가 될 수 있다 [확인 필요]. 법정동 코드표(지금은 `load_bjd_codes`가 상가정보 zip에서 만듦)와 격리 비율(CF3)·직전 대비 급감(CF4) 검사를 SQL로 옮겨야 한다.
  - C. 파싱까지 SQL. XML, zip, xlsx, shapefile을 PostgreSQL이 직접 다루기 어려워 제외.
- 결정과 이유: B (2026-11-12 사용자 결정). "받는 부분과 꺼내는 부분을 가르면 원천이 바뀌면 받는 쪽만, 요구사항이 바뀌면 SQL만 고친다"는 구조가 이 프로젝트가 보이려는 설계(변하는 부분과 유지할 부분을 구분)와 같다. 바꾸는 이유는 리니지를 뽑기 쉬워서가 아니라 변경 비용이 줄어서여야 하므로, S1·S2·S3를 다시 재서 확인한다. 리니지가 전 구간 이어지는 것은 따라오는 이득이다.
- 검증: (구현 후) 옮긴 출처마다 바꾸기 전 stg와 두 방향 `EXCEPT ALL` 차이 0, 격리 표 차이 0, 상품 파일 sha256 비교(측정 8과 같은 방법). S1·S2·S3를 측정 12~14와 같은 방법으로 다시 잰다.
- 결과와 남은 것: 어느 출처부터 옮길지, 처리 단위 멱등 방식, 생활이동을 어떻게 다룰지, 법정동 코드표와 CF3·CF4를 어디에 둘지는 차례로 정한다. 출처는 하나씩 옮기고 효과를 잰 뒤 넓힐지 정한다(change_resilience_plan.md 8절 7번).

  - A. 혼잡도. 장점: 원본 1,671행(65,169칸), 정제 0.13초로 작다. 다른 출처 의존이 없다. S1 기준값(측정 13)이 있다. 분기 파일에서 컬럼 이름이 실제로 바뀐 이력이 있다. 넓은 표(시간 칸 39개)를 세로로 푸는 정제라 리니지 파서가 따라가는지 시험하기 좋다. 단점: S2·S3 기준값은 이 출처에 없다.

## 결정 44. 리니지 추출 구조: 단계는 당근과 같게, 엔진은 Spark, 갱신은 작업과 도착 때 (P4)
- 상황: 결정 41에 따라 코드(SQL)를 파싱해 컬럼 리니지를 뽑는다. 참고한 구조(당근 컬럼 레벨 리니지 구축기)는 쿼리 수집 → sqlglot 파싱 → AST에서 의존 관계 추출 → 저장의 네 단계이고, Spark로 대량 쿼리를 병렬 파싱하고 Airflow로 주기 실행한다. 여기 입력은 dbt가 컴파일한 SQL 17개(`target/compiled/`)와 결정 42로 옮겨 올 정제 모델이다.
- 선택지:
  - A. 규모에 맞게. 파싱은 Python 한 프로세스, 갱신은 코드가 바뀔 때. 장점: 가장 단순하다. 단점: 엔진을 바꿀 수 있는 구조를 연습하지 못한다.
  - B. 참고 구조 그대로. Spark 병렬 파싱 + Airflow 주기 실행. 장점: 실무 구조를 그대로 따른다. 단점: 리니지는 코드나 원천 모양이 바뀔 때만 바뀌어 주기 실행은 같은 결과를 반복해서 만든다.
  - C. 네 단계는 같게, 파싱은 쿼리 하나만 받는 함수로 두어 엔진을 갈아끼울 수 있게. 장점: 엔진은 바뀌는 부분, 수집·파싱·추출·저장 흐름은 유지하는 부분으로 나뉜다. 단점: 함수 경계를 지키는 설계가 필요하다.
- 결정과 이유: C, 엔진은 Spark (2026-11-12 사용자 결정).
  - 규모는 이번 판단 기준에서 뺀다. 규모를 따지면 이 프로젝트에서 Spark는 쓸 수 없다(결정 24, 37). 그래서 Spark는 필요해서가 아니라 구조를 직접 다뤄 보려고 쓴다고 밝힌다(결정 28과 같은 동기). Spark는 이미 Airflow 이미지 안에 있다(`/opt/airflow/spark-venv`, 결정 35).
  - 갱신은 주기가 아니라 작업할 때마다, 데이터가 들어올 때마다 한다. 참고 구조는 들어오는 쿼리가 많아 주기 실행이 맞았지만, 여기 리니지는 코드를 고치거나 데이터가 들어와 빌드가 돌 때만 바뀔 수 있다. 결정 42로 원본을 원천 모양 그대로 담으면 새 필드가 들어온 것도 원천 쪽 지도를 바꾼다.
- 검증: (구현 후) 같은 파싱 함수를 Python 단독과 Spark로 각각 돌려 결과 간선 집합이 같은지, 시간과 메모리가 어떤지 적는다(결정 24, 37과 같은 방식. 이 규모에서 Spark 이점이 없으면 없다고 쓴다).
- 결과와 남은 것: sqlglot을 spark-venv와 requirements.txt에 넣고 CI에서 도는지 확인. 저장 형식, 정확성을 확인할 정답 세트, Airflow 어디에 붙일지(wh_load 뒤 등)는 차례로 정한다.

## 결정 45. 작업 순서: 리니지 추출기 먼저, 혼잡도 정제 이전은 그다음
- 상황: 정한 작업이 두 갈래다. 혼잡도 정제를 SQL로 옮기기(결정 42, 43)와 리니지 추출기 만들기(결정 40, 41, 44).
- 선택지:
  - A. 혼잡도 이전 먼저. 장점: 추출기를 처음부터 원본(jsonb) 구조에 맞춰 만든다. 단점: 원본 표 모양과 멱등 방식부터 정해야 하고, 이전 작업의 영향 범위를 지도 없이 확인해야 한다.
  - B. 리니지 추출기 먼저. 장점: 입력(컴파일된 SQL 17개)이 이미 있어 바로 시작한다. 지도를 들고 이전 작업에 들어가, 이전 전후 지도를 비교해 원천 → stg 구간이 이어진 것과 하류 영향이 없는 것을 지도로 보일 수 있다. 단점: jsonb 원천 처리는 이전 뒤에 추출기에 더해야 한다.
- 결정과 이유: B (2026-11-12, 사용자가 추천안을 승인). 바꾸기 전에 기준을 떠 두는 지금까지의 방식과 같다. 지도가 이전 작업의 기준이자 검증 도구가 되고, 이전 작업이 지도의 첫 실사용 사례가 된다.
- 검증: (구현 후) 혼잡도 이전 전후로 추출한 간선 목록을 비교한다.
- 결과와 남은 것: 추출기에서 "무엇을 관계로 볼지"부터 정한다.

## 결정 46. 리니지에 담을 관계: 값 관계 + 행 관계, 종류 표시 (P4)
- 상황: 지도에 어떤 연결을 선으로 그을지 정한다. 컬럼 사이 관계는 두 종류다. 값 관계는 결과 컬럼의 값을 만드는 입력 컬럼(복사, 계산, 집계)이고, 행 관계는 값은 만들지 않지만 어떤 행이 들어오는지를 정하는 컬럼(필터, 조인 조건, 그룹 기준, 정렬 후 고르기)이다. OpenLineage 컬럼 리니지 스펙도 DIRECT(IDENTITY, TRANSFORMATION, AGGREGATION)와 INDIRECT(JOIN, FILTER, GROUP_BY, SORT 등)로 나눈다 [확인 필요: 도입된 스펙 버전]. 이 프로젝트 예: `mart/dong_station.sql`의 `am_peak_congestion`은 값으로는 `fact_congestion.congestion`(max)에서 오고, 행으로는 `dow = '평일'`, `slot between '07:00' and '08:30'` 필터와 `line, sttn_no` 조인에 달려 있다. `nearest_station_id`는 `point <-> c.p` 정렬 후 하나 고르기에 달려 있다. 혼잡도 파일은 요일 컬럼 이름이 `요일구분` → `구분`으로 바뀐 기록이 있다(`docs/data_sources.md`). 요일 값 표기까지 바뀌면 `am_peak_congestion`은 오류 없이 비게 된다.
- 선택지:
  - A. 값 관계만. 장점: sqlglot `lineage()`가 주로 이 범위를 따라간다 [확인 필요]. 참고한 당근 예시와 같은 형태다. 단점: 위 `dow`, `slot` 같은 위험이 지도에 보이지 않는다.
  - B. 값 + 행 관계, 선마다 종류(DIRECT/INDIRECT와 세부 종류) 표시. 장점: 필터·조인 컬럼 변화로 행이 조용히 빠지는 위험을 놓치지 않는다. 종류를 보고 "값이 바뀌는 영향"과 "행이 빠지는 영향"을 나눠 볼 수 있다. OpenLineage를 도구로는 쓰지 않지만(결정 41) 분류 어휘를 빌려 표준과 맞추기 쉽다. 단점: WHERE, JOIN, GROUP BY, ORDER BY 절을 AST에서 직접 탐색해야 한다. 영향 후보가 늘어 종류로 걸러야 한다.
- 결정과 이유: B (2026-11-12, 사용자가 추천안을 승인). 이 프로젝트는 행정동 코드 조인과 시간대·요일 필터로 상품을 만들어, 행 관계를 빼면 가장 흔한 변화(코드 체계와 표기 변화)가 지도에서 사라진다.
- 검증: (구현 후) 정답 세트에 행 관계를 포함하고, 종류별로 맞은 것·놓친 것·틀린 것을 센다.
- 결과와 남은 것: 결과를 어디에 저장할지부터 정한다.

## 결정 47. 리니지 저장 위치: PostgreSQL, 전용 스키마 `lineage` (P4)
- 상황: 리니지를 읽는 쪽은 세 가지다. (1) 사람이 "이 컬럼이 바뀌면 어디까지 가나", "이 상품 컬럼은 어디서 왔나"를 묻는다. (2) P5 상품 계약에서 내보낼 때(`warehouse/export_product.py`) 깨는 변경의 원인을 적는다. (3) 혼잡도 이전 전후 지도를 비교한다(결정 45). 그래서 조회가 쉬워야 하고 회차별 이력이 있어야 한다.
- 선택지:
  - A. PostgreSQL 표. 장점: 읽는 쪽(사람의 SQL, Metabase, export_product.py)이 모두 PostgreSQL 쪽이다. 하류·상류 탐색이 `WITH RECURSIVE` 쿼리 하나다. Spark에서 쓰는 데 필요한 PostgreSQL JDBC 드라이버가 이미 이미지에 있다(`/opt/spark-jars/postgresql-42.7.14.jar`, Iceberg JDBC 카탈로그가 쓰는 것). 단점: 이력은 추출 회차 컬럼으로 직접 설계해야 한다.
  - B. 레포의 파일(JSON/CSV). 장점: git 이력이 그대로 버전이고 PR에서 지도 변화가 diff로 보인다. 단점: 탐색과 Metabase 연결이 불편하고 export_product.py가 파일을 따로 읽어야 한다.
  - C. Iceberg 표. 장점: 스냅샷이 그대로 이력이고 추출 엔진(Spark)과 같다. 단점: 읽는 쪽이 모두 Iceberg를 바로 읽지 못해 읽을 때마다 Spark가 필요하다. 결정 44에서 Spark를 쓰기로 한 것은 파싱 엔진이지 읽는 쪽이 아니다.
- 결정과 이유: A (2026-11-12, 사용자가 판단을 위임). 스키마는 `ops`가 아니라 전용 `lineage`로 둔다. `ops`는 실행·품질 같은 운영 상태(`ops.failure_log`, `ops.freshness`, `ops.quality`, `ops.product_file`)이고 리니지는 구조에 대한 메타데이터라 성격이 다르다. 이력은 추출 회차를 기록해 두 회차를 빼서 비교한다.
- 검증: (구현 후) Spark에서 JDBC로 쓰고 PostgreSQL에서 읽어 행 수가 같은지 본다. Metabase가 새 스키마를 읽는지 [확인 필요].
- 결과와 남은 것: 표와 뷰의 모양(데이터 모델)은 다음 결정에서 정한다.

## 결정 48. 리니지 데이터 모델: 원본 표 하나 + 목적별 뷰 (P4)
- 상황: 결정 47에 따라 `lineage` 스키마에 둔다. 파싱 결과에는 걸러야 할 것이 섞인다. `target/compiled/`의 SQL 82개 중 모델은 17개이고 65개는 dbt 테스트다. 컴파일된 SQL은 빌드 스키마(`wh_build`, `mart_build`)를 가리킨다. 파싱에 실패하거나 풀지 못한 컬럼도 생긴다. 쓰임새는 그림(표 단위), 하류 영향(S1, S4, S6), 상류 출처(P5), 회차 비교(결정 45)로 서로 다르다. 참고: 당근 컬럼 레벨 리니지 구축기는 한 표로 시작했다가 조회 목적이 늘자 원본 표 + 목적별 뷰로 바꿨다.
- 선택지:
  - A. 표 하나. 장점: 가장 단순하다. 단점: 테스트 제외, 스키마 이름 정리 같은 거르기가 모든 조회에 반복된다.
  - B. 원본 표 + 목적별 뷰. 장점: 원본은 파싱 결과를 있는 그대로 두고, 거르는 기준을 바꾸거나 새 뷰를 만들 때 다시 추출하지 않는다. 뷰가 쓰임새별 조회 창구가 된다. 단점: 재귀 뷰는 조회할 때마다 다시 계산한다(간선 수가 작아 문제는 아닐 것으로 본다 [미측정]).
  - C. 원본 표 + 목적별 표(미리 계산해 저장). 장점: 조회가 가장 빠르다. 단점: 원본이 바뀔 때마다 다시 만들어야 하고 지금 크기에서는 얻는 것이 없다.
- 결정과 이유: B (2026-11-12, 사용자가 추천안을 승인). 구성:
  - 원본 표 `lineage.edge_raw`: 간선(도착 테이블.컬럼 ← 출발 테이블.컬럼), 종류(결정 46), 나온 SQL 파일과 그 종류(모델/테스트), 추출 회차(추출 시각, git 커밋, 계기: 코드 작업/데이터 도착, sqlglot 버전). 파싱 실패와 풀지 못한 컬럼도 행으로 남긴다(CLAUDE.md 4절 4번). 파서 버전을 남기는 이유는 규칙 버전(P6)과 같다: 지도가 왜 달라졌는지 알 수 있게.
  - 목적별 뷰 4개: 테이블 단위 간선(최신 회차, 그림·Metabase), 하류 영향(재귀, 종류 표시, S1·S4·S6), 상류 출처(재귀, P5), 회차 비교(생긴 선과 사라진 선, 결정 45와 데이터 도착 때).
  - 참고 구조와 다르게 가는 곳: 테이블별 사용자 정보 뷰는 두지 않는다(레포 하나, 실행 경로 하나라 쓰는 곳이 없음, CLAUDE.md 4절 3번). "최근 30일" 같은 시간 창 대신 최신 회차를 현재 지도로 본다(쿼리 로그가 아니라 코드에서 뽑으므로).
- 검증: (구현 후) 원본 표 행 수와 파싱한 간선 수가 같은지, 뷰에서 테스트 SQL과 빌드 스키마 이름이 빠졌는지 확인한다.
- 결과와 남은 것: 정확성 확인 방법, 실행 연결 위치(결정 44의 갱신 계기), MCP로 제공할지는 차례로 정한다.

## 결정 49. 리니지 정확성 확인: 사람이 쓴 정답 + 변이 시험 (P4)
- 상황: 틀린 지도는 없는 것보다 위험하다. 파서 결과를 보고 맞는지 판단하면 파서가 놓친 것을 사람도 놓치므로, 파서와 독립된 정답이 필요하다.
- 선택지:
  - A. 사람이 정답 작성. 모델 몇 개의 컬럼 관계(값·행 관계)를 손으로 적고 파서 결과와 대조해 맞은 것·놓친 것·틀린 것을 센다. 장점: 두 종류 관계를 모두 적을 수 있다. 단점: 사람이 놓치면 정답도 놓친다. 쉬운 모델만 고르면 점수가 높게 나온다.
  - B. 변이 시험. 입력 컬럼 하나의 값을 일부러 바꿔 빌드 스키마에 다시 빌드하고, 어느 출력 컬럼과 행이 실제로 바뀌는지 두 방향 `EXCEPT ALL`로 본다. 실제로 바뀐 것이 정답이다. 장점: 사람과 파서 둘 다에서 독립된 정답이다. 필터 컬럼을 바꾸면 행이 빠지는 것처럼 행 관계도 실행으로 드러난다. 필요한 장치가 이미 있다(빌드 스키마에 빌드하는 구조, 결정 30·32, 두 방향 대조, 측정 8·9). 단점: 관계마다 다시 빌드해 느리다(dbt build 약 1분, 측정 8). 바꾼 값이 우연히 결과를 바꾸지 않으면 관계를 놓친다.
  - C. A + B. 손 정답으로 넓게 보고, 그중 일부 관계를 변이 시험으로 실행해 확인한다.
- 결정과 이유: C (2026-11-12, 사용자가 추천안을 승인). 혼잡도 요일 표기 변화처럼 조용히 행이 빠지는 위험을 실제로 일으켜 보고 지도가 잡는지 확인할 수 있다. 규칙: (1) 모델은 어려운 패턴 위주로 고른다(CTE, LATERAL 정렬 후 고르기, `percentile_cont` 같은 집계, PostGIS 함수, 필터). `dong_station`, `dong_rent_summary`를 포함한다. (2) 정답은 파서를 돌리기 전에 쓰고 커밋해 git 시각으로 순서를 남긴다. (3) 변이 시험은 실제 `wh`·`mart`를 건드리지 않고 빌드 스키마에서만 한다.
- 검증: 측정 기록에 종류별(DIRECT/INDIRECT) 맞은 것·놓친 것·틀린 것 수, 변이 시험 관계 수와 결과를 적는다. 놓친 패턴은 고치기 전에 분류해 기록한다.
- 결과와 남은 것: 정답 모델 목록과 변이 시험 관계 고르기는 구현 직전에 한다.

## 결정 50. 리니지 추출 연결: 별도 lineage DAG, wh_load 뒤 Asset으로 (P4)
- 상황: 결정 44의 갱신 계기(코드 작업, 데이터 도착)는 둘 다 dbt build로 모인다. 데이터가 들어오면 스테이징 Asset으로 `wh_load`가 돌고(`dags/wh_load.py`, `AssetAny`), 코드를 고쳐도 `wh_load`나 `dbt build`로 확인한다. 추출기의 입력(`target/compiled/`)도 `wh_load`의 `dbt_build`가 만든다. 지금 흐름은 `dbt_build >> swap_schemas >> export_product`다.
- 선택지:

  - B. 별도 lineage DAG를 두고, wh_load가 끝나면 Asset 알림으로 돌린다. 코드 작업 뒤에는 손으로도 돌린다. 장점: 실패가 서로 번지지 않고 리니지만 따로 다시 돌린다. 레포에 이미 같은 패턴이 있다(`dags/assets.py`, 스테이징 → wh_load, 결정 29). 단점: Asset 하나와 DAG 파일 하나가 는다.

- 결정과 이유: B (2026-11-12, 사용자가 추천안을 승인). 리니지는 상품을 만드는 흐름의 일부가 아니라 그 흐름을 관찰하는 메타데이터라 실패가 번지지 않게 뗀다.
- 검증: (구현 후) wh_load 수동 실행 뒤 lineage DAG가 Asset으로 한 번 도는지, lineage를 일부러 실패시켜도 wh_load와 상품은 영향이 없는지 본다.
- 결과와 남은 것: P5에서 내보내기가 리니지를 읽게 되면 순서 의존이 생기므로 그때 다시 본다. 나중에 Kubernetes로 옮길 때(GH프로젝트 계획) 걸리는 점: 지금은 lineage 작업이 wh_load가 같은 컨테이너 파일시스템에 남긴 `target/compiled/`를 읽는다. 작업마다 다른 파드에서 도는 실행 방식에서는 이 파일이 보이지 않으므로, 공유 볼륨에서 읽거나 lineage 작업이 스스로 `dbt compile`을 하도록 바꿔야 한다.

## 결정 54. 간선 추출 규칙: sqlglot lineage + scope 훑기 보완 + 보정 4개 (P4)
- 상황: 측정 16에서 sqlglot `lineage()`는 값 관계(DIRECT)만 주고 필터·조인 같은 행 관계(INDIRECT)는 주지 않았다. 또 LATERAL `select s.*` 과다 귀속, `count(*)` 출처 없음, 별칭 이름, jsonb 키가 컬럼 전체로 나오는 문제를 봤다.
- 선택지:
  - A. `lineage()`만 쓰고 행 관계는 사람이 손으로 더한다. 장점: 구현이 가장 작다. 단점: 결정 46(행 관계 포함)을 지키지 못하고 손 작업이 코드와 어긋난다.
  - B. AST를 처음부터 직접 훑어 값·행 관계를 모두 만든다. 장점: 모든 규칙을 통제한다. 단점: CTE·서브쿼리·별칭 풀이를 다시 만드는 일이라 크고 틀리기 쉽다.
  - C. 값 관계는 `lineage()`, 행 관계는 `optimizer.scope.build_scope`로 scope마다 WHERE, JOIN ON/USING, GROUP BY, HAVING, ORDER BY, 윈도우, 집계 FILTER·CASE 조건을 훑어 보완하고, 보정 4개(별칭 → 실제 테이블, `count(*)` → 테이블의 행 `*`, jsonb `->>` → `raw.키`, 풀지 못한 것은 `unresolved`로 남김)를 더한다.
- 결정과 이유: C (2026-11-13, 사용자가 판단을 위임). 측정 16의 시제품에서 scope 훑기로 `dong_station`의 `dow`, `slot` 필터와 조인·정렬 컬럼이 나왔다. 이미 되는 일(CTE·별칭 풀이)은 라이브러리에 맡기고 안 되는 부분만 더한다. 행 관계를 붙이는 규칙: WHERE·INNER JOIN·GROUP BY·HAVING·정렬은 그 scope를 거치는 모든 출력 컬럼, LEFT JOIN의 ON은 오른쪽 소스에서 온 출력 컬럼에만(왼쪽 행은 빠지지 않으므로), 집계 FILTER·CASE 조건은 그 식이 든 출력 컬럼에만. LATERAL 과다 귀속은 고치지 않고 정답 대조에서 "틀림"으로 먼저 센다.
- 새 의존성: sqlglot. 이유는 PostgreSQL 방언 파싱, qualify, lineage, scope를 한 라이브러리가 주고 순수 Python이라 Spark 실행기에서도 그대로 돈다는 것. 사전 시험 버전 30.31.0으로 `requirements.txt`와 spark-venv에 같이 고정한다.
- 검증: 정답 대조와 변이 시험(결정 59).
- 결과와 남은 것: 상세 규칙은 `docs/design_change_resilience.md` 1.4절.

## 결정 67. 값 관계도 scope 해석기로 뽑는다 (결정 54 수정, P4-2)
- 상황: 결정 54는 값 관계(DIRECT)를 sqlglot `lineage()`로, 행 관계(INDIRECT)를 scope 훑기로 나눠 뽑기로 했다. 구현해 보니 행 관계에도 "별칭을 scope를 건너 물리 표 컬럼까지 따라가는" 해석기가 똑같이 필요했다. 그리고 `lineage()`는 출력 식 안의 컬럼을 위치 구분 없이 모두 잎으로 돌려준다. 그래서 CASE 조건, 집계 FILTER(where), 창 PARTITION/ORDER의 컬럼이 값 출처로 섞인다(설계서 1.4가 CONDITIONAL, WINDOW로 나누려던 것).
- 선택지:
  - A. 결정 54대로 `lineage()` 결과에서 조건 자리 컬럼을 사후에 걸러낸다. 장점: 라이브러리 재사용. 단점: lineage 노드에는 "이 잎이 식의 어느 자리에서 왔나"가 없어 거르기 어렵다. 측정 16의 LATERAL `s.*` 과다 귀속도 따로 보정해야 한다.
  - B. qualify + build_scope 위에 해석기 하나(`Resolver`)를 두고, 값 관계와 행 관계를 모두 이 해석기로 만든다. 식 나무에서 컬럼의 위치(If.this, Filter.expression, Window의 partition/order)로 조건 자리를 판정한다.
- 결정과 이유: B (2026-11-13, 위임 작업). 해석기가 하나면 같은 컬럼을 값으로 따라가든 조건으로 따라가든 같은 길을 간다. qualify가 `s.*`를 펼친 뒤 고른 컬럼 하나만 따라가므로 측정 16의 과다 귀속이 생기지 않는다(시험으로 고정). `lineage()`는 쓰지 않는다. 별칭 풀이, `*` 펼치기, scope 나누기는 여전히 sqlglot에 맡긴다(결정 54의 "이미 되는 일은 라이브러리에").
- 검증: 측정 19. DIRECT 78개 모두 맞음, 틀림 0. `tests/test_lineage_edges.py`에 패턴별 시험 9묶음을 넣었다. 조건 자리 판정과 LEFT JOIN 규칙을 일부러 망가뜨리면 시험이 실패하는 것도 확인했다.
- 결과와 남은 것: `lineage/edges.py` 약 200줄. 함수 LATERAL(`jsonb_each_text`)과 jsonb `->>` 키 보정(설계서 1.4)은 쓰는 곳이 생기는 혼잡도 이전 때 더한다.

## 결정 68. 조인 조건이 거쳐 간 파생 표의 행 조건은 그 조인 결과에 번진다 (설계서 1.4 규칙 4 보완, P4-2)
- 상황: 첫 정답 대조(측정 19)에서 INDIRECT 놓침 6개, subkind 차이 17개가 모두 한 패턴이었다. 하나는 `commute_od`의 `by_code`(최근 6개월 필터, 출발·도착 그룹)를 INNER JOIN으로 붙였는데, 그 행 조건이 `by_code`를 거치지 않는 출력(`origin_dong_id` 등)에 붙지 않은 것이다. 다른 하나는 `dong_station`이 LATERAL k가 고른 역으로 peak을 LEFT JOIN하는데, k의 정렬이 `am_peak_congestion`에 붙지 않은 것이다. 규칙 4("출력이 거쳐 간 scope의 절만")가 조인 조건 컬럼이 거쳐 간 scope를 보지 않기 때문이다.
- 선택지:
  - A. 규칙 그대로 두고 한계로 기록한다. 단점: S4·S6 같은 영향 질문에서 "최근 6개월 필터를 바꾸면 출발 동 컬럼도 바뀐다"를 놓친다.
  - B. 조인 ON(그리고 WHERE 등 모든 절)의 조건 컬럼을 풀며 거쳐 간 파생 표가 있으면, 그 파생 표의 절도 그 조건과 같은 범위(INNER면 모두, LEFT면 오른쪽에서 온 출력)에 붙인다. 상관 참조로 바깥 scope에 닿는 경우는 순환을 막으려고 자기와 바깥 scope를 건너뛴다.
- 결정과 이유: B (2026-11-13, 위임 작업). 정답 줄에 맞추려는 예외가 아니라 의미 규칙이다. 조인 키 값이 "파생 표가 어느 행을 남겼나"에 달려 있으면, 그 선택 조건은 조인 결과의 행을 바꾼다. LATERAL `cross join ... limit 1`처럼 행을 거르지 않는 조인은 조건 컬럼이 없어 번지지 않는다(시험으로 고정: LATERAL 정렬이 `c.id`에 붙지 않음).
- 검증: 측정 19. 놓침 6 → 0, 틀림 0 → 0. 고치는 중에 함께 찾아 고친 것 두 가지: 하위 쿼리 안의 절을 바깥 절 이름(FILTER)으로 덮어쓰던 것, `ORDER BY "target_ym"`처럼 select 별칭을 가리키는 컬럼을 풀지 못하던 것.
- 결과와 남은 것: subkind 차이 10개가 남았다. `commute_od`의 `split`(group by dong_cd_2021)을 조인하는 조건 때문에 GROUP_BY가 모든 출력에 붙는데, 정답은 JOIN으로만 적었다. 이 규칙으로는 맞는 동작이라 정답과 해석이 다른 것으로 기록하고, 정답은 고치지 않았다(정답이 파서에 끌려가지 않게, 결정 49). 아침 검토에서 사용자가 정한다.

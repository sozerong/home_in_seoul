# 보증 기록: 지켜야 하는 성질과 그 증명

파이프라인이 지켜야 하는 성질(멱등, 동등, 원자성 등)마다 **무엇을 어떻게 시험해 증명했는지, 근거가 무엇인지**를 모은다. "돌아간다"가 아니라 "이 성질이 성립한다는 것을 이 방법으로, 이 조건에서 확인했다"를 남기는 곳이다. 측정의 숫자는 `docs/measurements.md`, 왜 그렇게 만들었는지는 `docs/decisions.md`, 증명 중 만난 오류는 `docs/failure_analysis.md`에 있고 여기서는 번호로 가리킨다.

## 0. 규칙

- 성질 하나를 증명하면(처음이든 다시든) 2절 해당 표에 한 줄을 더한다. 칸: 대상, 방법, 근거(측정·결정·커밋), 조건(데이터 범위, 횟수), 강도, 한계.
- **강도**를 반드시 적는다. 한 번 증명한 것과 매 실행 지켜지는 것은 다르다.
  - ① 1회 증명: 그때 손으로 확인했다. 코드가 바뀌면 다시 증명해야 한다.
  - ② 재현 가능: 증명 절차가 스크립트로 남아 누구나 다시 돌릴 수 있다(`measure/` 등).
  - ③ 매 실행 강제: dbt 테스트, 관문, CI, 계약 검사가 매번 확인하고 어기면 실패한다.
- **실패한 증명 시도도 남긴다.** 첫 대조에서 차이가 나왔다면 그 차이, 원인, 고친 뒤 결과를 함께 적는다(원인은 failure_analysis.md 항목으로).
- 방법이 증명하지 못하는 것(한계)을 적는다. 1절의 방법별 한계를 참고한다.
- 증명하지 않았거나 깨진 성질은 3절에 적는다. 증명된 것처럼 쓰지 않는다.

## 1. 증명 방법과 그 방법이 보이는 것

| 방법 | 보이는 것 | 보이지 않는 것 |
|---|---|---|
| 두 방향 `EXCEPT ALL` (A − B와 B − A가 모두 0행) | 중복 횟수까지 포함해 행의 다중집합이 같다. NULL끼리는 같다고 본다 | 컬럼 이름·순서·타입(→ `pg_attribute` 비교를 덧붙인다), 행 순서, 부동소수 끝자리가 다른 경우는 차이로 나온다 |
| `pg_attribute` 비교 | 컬럼 이름, 순서, 타입이 같다 | 값 |
| 행 수와 합계 비교 | 크기와 총량이 같다 | 값이 서로 바뀌어도 같게 나올 수 있다. 약한 증거다 |
| 파일 sha256 비교 | 바이트까지 같다 | 정렬과 직렬화가 결정적이어야 의미가 있다(결정 33). 다르면 어디가 다른지 모른다 |
| 실패 주입 | 실패 경로가 실제로 돌고, 설계한 대로 멈추거나 되돌아간다 | 주입하지 않은 다른 실패 |
| 변이 시험 (값 하나를 바꾸고 실제로 바뀐 것을 본다) | 영향 예측(리니지)이 실제 영향을 놓치지 않는가(재현율) | 고르지 않은 경로. 예측이 넓은 것(정밀도)은 따로 센다 |
| 정답 대조 | 추출기가 사람이 쓴 정답과 맞는가 | 정답과 추출기를 같은 작성자가 썼다는 한계 |
| 대조군 (변이 없는 시험 환경 = 실제) | 시험 환경이 실제를 그대로 재현한다. 이게 없으면 변이 시험 결과를 믿을 수 없다 | |

## 3. 증명하지 않았거나 깨진 것

| 성질 | 상태 | 근거 | 다음 |
|---|---|---|---|
| 원본은 고치지 않는다 | 규칙으로만 지킨다. 시험은 새 배치 키와 뷰(`raw_t`, `raw_mut`)로만 했다 | 측정 25, 30, 31 | 강제하려면 적재기 밖 역할에서 `raw`에 UPDATE·DELETE 권한을 빼는 방법이 있다(미결정) |
| 상품 0행이면 실패 | **증명 안 됨.** 변이 M7에서 모든 수집일의 표기를 바꾸자 기댈 직전 승인 배치가 없어 `rent_listing`이 0행이 됐다. 이때 내보내기가 실패하는지는 시험하지 않았다(변이 시험은 내보내지 않음) | 측정 31 | 실제 운영에서는 원본 과거분이 바뀌지 않아 직전 승인본이 남는다. 다만 처음 넣는 처리 단위는 기댈 곳이 없다. [확인 필요: 마트·상품 0행 검사가 있는지] |

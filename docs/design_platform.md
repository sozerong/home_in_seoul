# 서울 동네 찾기: 데이터 플랫폼 전환과 원인 확인 설계 (v22)

직접 확인한 결과: docs/evidence/ (results.txt, pg_tests.sql, pg_tests.sh). 검토 기록의 rv10~rv16 등 경로는 클라우드 작업 공간의 것이라 레포에 없다

## 0. 목표, 규칙, 먼저 정할 것
- 사용자 방향: 데이터 플랫폼이 중심. 여러 출처의 데이터를 다른 사람이 쉽게 확인하고 가져가게 한다. 가져올 데이터를 더 찾는다. 다른 부동산 플랫폼을 기준으로 삼는다. 근거를 알고리즘·자료구조·컴퓨터 구조까지 내려가 CS 기본기를 보인다. 평가 기준은 데이터 플랫폼 3년차.
- 멘토(docs/mentoring_2026-11-21.md): 플랫폼은 "모델러나 분석가가 데이터를 쉽게 쓸 수 있게 도구나 환경을 제공하는 쪽", 이 프로젝트는 파이프라인에 가깝다(13~14행). DuckDB는 spill이 왜 안 되는지, 메모리가 왜 쌓이는지, 새 프로세스가 왜 해결하는지(17~21행). OOM 때 다른 DB도 생각했는지(25행). 멘토 문서 2.1의 이야기 순서: OOM 형태 → 원인 → 원인에 맞춘 해결 → 영향 범위 분리.
- **이 설계의 무게중심:** 플랫폼 능력을 실제로 만드는 단계 3이 결과물이다. 진행 순서는 단계 0 → (D0~D2 결정) → 단계 3과 단계 1·2를 번갈아 진행이다. 단, 엔진 실험 묶음이 도는 동안에는 단계 3 변경을 운영에 배포하지 않고, 단계 3의 내보내기 시험(B-a·B-c·B-i)은 임시 product 루트에서만 돌린다(ops_snapshot이 product/ 최신 폴더 sha256을 비교하므로, 28~29행). 단계 3은 엔진 실험 결과에 기대지 않으므로 엔진 쪽이 길어져도 결과물이 남게 단계 3의 B-a·B-b를 먼저 끝낸다. 엔진 실험은 멘토의 세 질문과 원인별 해결에 답하는 것만 남기고, A5m·C3 상세·D9 대규모 측정은 D10·D11 뒤로 뺀다.
- **사용자 결정(2026-11-22, decisions.md 결정 113): 상품을 공개 정적 사이트(GitHub Pages, 데이터 전용 새 레포)로 배포하고, 카탈로그 페이지·파일과 manifest·URL 조회 예시·브라우저 안 SQL(DuckDB-WASM)을 둔다. 공개 범위는 이용조건을 다시 찾아 출처를 붙여 공개 가능한 컬럼까지. 확인은 작업 PC 밖 에이전트의 인수 시험. 구현 지시는 docs/handoff_pages.md.** 이 결정으로 D2는 "파일 + 공개 정적 사이트", D3는 "일부 클라우드(정적 호스팅)"로 정해졌고, B-e의 "작업 PC 밖 경로"는 이 사이트다.
- **D0(사용자, 단계 0의 P3 결과를 본 뒤 가장 먼저): 쓰는 쪽.** A 내부 분석가·모델러 / B 외부 부동산 플랫폼(결정 12) / C 둘 다.
- 규칙 출처: CLAUDE.md(설계 결정은 사용자, 체크포인트에서 멈춤, 수치는 실행값만) + docs/handoff_platform_cs.md 0.4·3.1(운영 무손상: 앞뒤 measure/ops_snapshot.py 같음, 실행 전 예측 파일과 sha256). ops_snapshot은 표 행 수만 비교하므로(26행) 실험이 쓰는 운영 표(stg 생활이동 세 표)는 앞뒤로 행 순서와 무관한 해시 합(sum(hashtext(행 전체 글자)))도 비교한다(약 4,500만 행, 앞뒤 각 1회, 시간은 4절 "운영 해시 비교" 행).
- **원인은 세 단계로 적는다(handoff 0.4의 둘째 규칙, 52~54행):** 측정된 현상 / 알고리즘·자료구조 수준의 이유 / 컴퓨터 구조·운영체제 수준의 이유. 셋째 단계의 자료로 모든 실행에서 wait4가 이미 돌려주는 ru_minflt·ru_majflt(페이지 폴트), ru_nvcsw·ru_nivcsw(자발·비자발 문맥 전환)와 /proc/<pid>/status의 VmHWM·RssAnon·RssFile을 남긴다(자식을 거둔 뒤에는 /proc가 사라지므로 래퍼가 실행 중 1초마다 표본을 찍고, 마지막 표본을 최종값으로 씀. 죽은 실행은 마지막 표본까지만 남는다고 적음)(지금 measure/duckdb_sql.py 427~430행은 ru_maxrss만 씀). 확인 못 한 단계는 [확인 필요]로 둔다.
- **판정 규칙(모든 실험):**
  - 비교의 기준 조건과 가장 좋은 조건은 3회 이상, 중간 조건은 1회(모양 확인, 반증에 안 씀). 반복마다 같은 입력을 한 번 다 읽는 예열을 앞에 둔다.
  - 기준 폭: 비교마다 실행 전에 예측 파일에 적는다. 정하지 않으면 기준 조건 중앙값의 10%.
  - 세 갈래로만 판정한다. "차이 있음": 두 조건의 실행값이 완전히 갈리고(한쪽의 모든 값이 다른 쪽의 모든 값보다 작음) 중앙값 차이가 기준 폭보다 큼. 완전히 갈림의 우연 확률은 정확 순위 검정으로 3회 대 3회에서 방향을 예측 파일에 적었으면 단측 1/20, 아니면 양측 2/20. "같음": 중앙값 차이가 기준 폭 이내이고, 두 조건의 모든 실행값이 기준 조건 중앙값 ± 기준 폭 안에 듦(갈림 여부와 무관. 값이 아주 고르면 작은 차이도 완전히 갈리므로 갈림만으로 차이를 주장하지 않고, 크게 흔들리면 중앙값만 가까워도 같다고 하지 않는다). 나머지(갈리지 않았고 차이가 기준 폭보다 큼, 또는 중앙값은 가깝지만 값이 기준 폭 밖으로 흔들림)는 "판정 불가"로 적고, 반복을 더하기 전에 흔들림의 원인(캐시 상태, 같은 시간 다른 작업)을 먼저 통제한다. 범위 폭 자체는 표본을 더해도 줄지 않으므로 "차이 있음"의 근거로 쓰지 않는다.
  - 갈래 기록: 같은 명령이 엔진 안에서 두 갈래로 나뉠 수 있다(V36: 같은 입력·설정 3회 중 흘림 갈래 2회, 흘림 없는 갈래 1회, 캐시를 비워도 나뉨). 그래서 모든 DuckDB 실행에 임시 > 0 여부와 HASH_TABLE 최대를 남기고, "흘림 있음/없음" 조건은 설정이 아니라 그 갈래로 실제 끝난 실행으로 정의한다. 한 조건에서 갈래가 섞이면 갈래 비율을 결과로 적고, 갈래마다 3회가 모일 때까지 반복을 더한다(상한 9회, 넘으면 판정 불가).
  - 실패한 실행(DuckDB 예외, 137)은 수치 비교에서 빼고 조건별 "실패 n/m"으로 따로 적는다. 한 조건이 모두 실패하면 그 비교는 수치 판정 없이 "그 조건은 실패"가 결과다.
  - Spark 묶음은 비교하는 두 조건을 모두 5회 돌린다(같은 일이 2,720~3,705초로 흔들린 기록, 측정 52). 5회 대 5회에서 완전히 갈리면 단측 1/252, 양측 2/252.
  - 결과 종류: 완주 / DuckDB 예외 / 종료 코드 137(cgroup) / 기타. DuckDB 예외 문구("failed to allocate data of size", "could not allocate block of size")는 그 순간 요청한 할당의 종류만 말하고 둘 다 memory_limit 안에서 센다(V28). 메모리를 채운 주체는 실패 직전 duckdb_memory() 태그별 기록으로 판정한다. 137이면 DuckDB가 세지 않는 몫(할당기 보유, Python, 추적되지 않는 할당)을 본다.
  - 메모리 최대는 프로세스 최대 RSS(ru_maxrss, 측정 51의 "자식 최대 RSS")를 쓴다. 한 프로세스가 여러 배치를 도는 실험은 배치 경계마다(각 배치 끝, DROP 뒤) 같은 시각에 VmRSS와 duckdb_memory() 합을 함께 남긴다. cgroup memory.max_usage_in_bytes는 페이지 캐시를 포함해(측정 42 "대부분 페이지 캐시") 메모리 최대로 쓰지 않는다.
  - 실험 세트마다 Iceberg metadata.json을 고정하고, 운영 stg가 만들어진 스냅샷과 같은지 확인한다.
  - 운영 고정: 정기 실행이 실험 중 표를 바꾼다(molit_rent 매주 월 13:00, seoul_api 매주 월 13:30, 어느 하나가 끝날 때마다 Asset으로 wh_load(dags/wh_load.py 23행 AssetAny라 월요일에 2회 돎, decisions.md 382행. 전월세만 바뀌어도 wh 전체 재생성)·상품 내보내기, file_living_migration 매월 21일 13:00 시작 7일 센서. 일정은 decisions.md 379·382행(2026-11-03 변경, 235행의 월 05:00은 옛 값)). 그래서 (1) 실험 묶음 시작 전 사용자가 세 DAG(molit_rent, seoul_api, file_living_migration)를 일시정지하고 끝나면 푼다(D14, 사용자 일). (2) 같음 비교의 기준은 운영 표가 아니라 묶음 시작 때 운영 stg 세 표를 DuckDB postgres 확장으로 읽어 /exp에 떠 둔 Parquet 사본과 고정 metadata.json이다. 일시정지를 못 하면 ops_snapshot 불일치 중 정기 실행 기록(dag_run)으로 설명되는 것은 실험 탓이 아님으로 적는다.

## 2. 받는 쪽 가치 가설과 근거
- 가설: 받는 쪽이 덜 하게 되는 일은 공공 원천 여러 개를 공통 키로 맞추고, 늦은 신고를 반영하고, 품질 오류를 격리한 결과를 계속 받는 것.
- 이용조건(data_contract.md 5절): 전월세·상가 "제한 없음", 역사마스터 공공누리 1유형, 혼잡도는 열린데이터광장 3유형(변경금지)과 공공데이터포털 "제한 없음"이 다름, 생활이동 표시 없음, SGIS 경계는 약관상 타인 제공·영리행위 불가, 연속지적도는 경로마다 다름. D0 = B·C면 일부 상품 컬럼이 걸릴 수 있어 P3가 D0보다 먼저다.
- 직접 만들 때 비용 근거: CLAUDE.md 7절의 알려진 데이터 문제 11개, 실패 분석 중 데이터 정합 문제(P1에서 셈).
- 시장 근거(약함): 크몽 "부동산 공공데이터 수집/DB/지도표기"(5만~40만 원, "최근 1개월 내 거래는 신고 대기로 누락될 수 있습니다"), Apify KB 시세 스크레이퍼(V25). 이 프로젝트는 지난달 신고 증가를 다시 받는다(측정 1). 기업 정기 구매 공개 사례는 못 찾음.
- 기능 수요(B2C): 전세 위험(V21·V22), 시세 변화(V21), 출퇴근(호갱노노 자차 기준, 대중교통 기준 못 찾음, V23), 코드 체계(네이버 부동산 10자리 법정동, V24). 후보 출처에 한국부동산원 통계(V20·V27).

### 단계 1: 도구 변경 (사용자 승인 D12, 다음 결정 번호로 기록)

# 판단 기록 (2026-11-13 밤, 사용자 위임 작업)

사용자가 자는 동안 `docs/design_change_resilience.md` 0절 순서대로 진행하며 내린 판단을 시간순으로 적는다. 설계 결정으로 남길 만한 것은 `docs/decisions.md`에 결정 번호로 옮기고 여기에는 번호만 단다. 아침에 이 파일부터 읽으면 된다.

판단 기준 (사용자가 준 방향, 2026-11-13): **변하는 부분과 유지할 부분을 구분해, 변화가 와도 고칠 곳이 적은 구조.** 참고 사례는 당근 "컬럼 레벨 리니지 구축기"(2025-12-04). 그 글의 구조(sqlglot 파싱 → Spark 병렬 → raw 표 + 목적별 뷰 → MCP)는 우리 설계(결정 41, 44, 47, 48, 51)와 같고, 글의 교훈 "주요 쿼리 패턴부터 커버리지를 쌓고, 작게라도 실제로 쓰이는 상태를 먼저"를 범위 판단의 기준으로 쓴다.

## 판단 목록

1. **S6a 업종은 헬스장 R10307** (사용자 선택). 측정 17.
2. **S6a에서 다수결 대응표 영향을 추가로 쟀다** (사용자 승인). 읽기 전용 트랜잭션은 임시 표 생성도 거부해서, 더할 행을 배열 파라미터로 넘기는 방식으로 바꿨다. 결과: 대응은 그대로, 상품 `dong_mois_map` 417행의 `stores`, `share` 값이 바뀜.
3. **참고 글 확인.** Medium이 자동 요청을 403으로 막아 내장 브라우저로 읽었다. 우리 설계와 다른 점: 당근은 쿼리 로그(INFORMATION_SCHEMA.JOBS)를 읽고, 우리는 dbt 컴파일 SQL을 읽는다(결정 41, 정제 적재가 INSERT VALUES라 로그에 원천 필드가 없음). 당근은 행 관계(필터·조인) 구분을 언급하지 않는다. 우리는 측정 15에서 실제 영향이 필터로 이어진 사례가 있어 행 관계를 넣는다(결정 46). 이 차이는 그대로 유지한다.
4. **S6b 실행 방식.** Airflow 컨테이너가 꺼져 있어(Exited 255) `docker compose run --rm --no-deps`로 일회성 컨테이너를 띄웠다. 스케줄러를 켜면 밀린 정기 실행이 돌 수 있어서 피했다. 측정 스크립트의 `psutil` import는 함수 안으로 옮겼다(spark-venv에는 없음). 측정 18.
5. **S6b "흔한 고침"은 바꾸기, 요구는 더하기.** 실행으로 잰 것은 바꾸기(3곳)다. 더하기는 stg 표 모양(방향 컬럼, PK)까지 번져서, 실행하지 않고 고칠 곳만 읽어서 셌다. 이유는 결정 65(레포·DB를 건드리지 않음) 때문이다. 그 과정에서 `commute_od`에 방향 조건이 없어 조용히 섞이는 경로를 찾아 측정 18에 적었다.
6. **정답은 규칙이 아니라 의미로 썼다** (결정 66). 설계서 규칙을 아는 사람이 규칙대로 쓰면 규칙의 빈틈이 점수에 안 보인다. `dong_station.am_peak_congestion`에 LATERAL k의 정렬·필터를 붙인 4줄이 대표적인 "규칙 밖" 줄이다. 6개 모델 353줄.
7. **정답은 사용자 검토 전에 커밋한다.** 설계서는 "사용자가 검토하고 커밋"이라고 하지만, 더 중요한 조건은 "파서 코드보다 먼저 커밋"(결정 49)이다. 밤에 파서까지 가려면 먼저 커밋해야 한다. 그래서 정답만 담은 커밋을 하나 만들었고(push 안 함), 아침 검토로 바뀌는 줄은 별도 커밋으로 남겨 구분한다.
8. **값 관계도 scope 해석기로** (결정 67, 결정 54 수정). sqlglot `lineage()`는 CASE 조건과 집계 FILTER의 컬럼을 값 출처로 섞어서 쓰지 않았다.
9. **`dbt compile`은 DB가 있어야 돈다.** 네트워크 없는 컨테이너에서는 `--no-introspect`를 줘도 실패했다. 그래서 추출기는 wh_load가 남긴 `target/`을 읽고, CI 시험은 시험 안에 적은 SQL로 돌린다.
10. **첫 점수를 먼저 기록하고 고쳤다** (측정 19, 결정 68). v1: INDIRECT 놓침 6(한 패턴). v2: 놓침 0, 틀림 0. 남은 subkind 차이 10개는 정답을 고치지 않고 해석 차이로 남겼다(아침 검토).
11. **정답과 파서를 같은 작성자가 썼다는 한계**를 측정 19에 적었다. 그래서 변이 시험(실행 기반)을 건너뛰지 않는다.
12. **행 집합 간선은 제안으로만 남겼다.** S6a의 `dong_mois_map` 결합은 컬럼 값이 아니라 "업소가 몇 개 들어오나"(행 집합)를 따라 흐른다. 모델마다 FROM·JOIN 표에서 `원천.* → 대상.*` 간선을 더하면 지도에 잡힌다. 설계서에 없는 확장이고 정답 기준(결정 66)도 바꿔야 해서, 사용자가 정하도록 남긴다. 측정 20.
13. **`downstream` 뷰는 경로 배열 대신 (출발, 도착, 깊이, 행 관계 여부) 상태로 UNION 중복 제거.** 설계서는 "지나온 노드 배열로 순환을 막는다"고 했다. 하지만 경로 배열을 들고 다니면 경로 수만큼 행이 늘어난다(INDIRECT 간선이 출력 컬럼마다 붙어 분기가 많다). 그래서 상태를 줄이고, DAG라 순환이 없음을 근거로 깊이 20 제한만 두었다. 전체 2,867쌍, 조회 0.24초.
14. **추출 회차는 파싱 실패가 있어도 success로 남기고 명령은 실패시킨다.** 뷰는 `status='ok'` 간선만 읽으므로 실패 파일 몫만 빠진다. DAG는 실패로 끝나서 사람에게 닿는다.
15. **엔진 비교는 둘 다 같은 컨테이너에서 쟀다.** Windows .venv와 컨테이너를 섞으면 운영체제와 파일시스템 차이가 엔진 차이에 섞인다. 메모리는 cgroup `memory.peak`가 이 커널에 없어 `/proc/*/status` VmRSS 합을 0.1초마다 표본으로 쟀다. 표본이라 순간 최대는 놓칠 수 있다(측정 21에 적음).
16. **컨테이너에서 git 커밋이 비던 문제를 고쳤다.** 바인드 마운트한 저장소는 소유자가 달라 git이 거부해 `lineage.run.git_commit`이 비었다(회차 2~8). MCP 응답의 "지도가 코드보다 늦었나" 판단이 이 값을 쓰므로 `git -c safe.directory=<루트>`로 그 호출에서만 검사를 껐다. 전역 git 설정은 건드리지 않았다.
17. **Asset URI를 잘못 적어 DAG 8개가 한꺼번에 깨졌다가 바로 고쳤다.** `assets.py`를 모든 DAG가 불러오므로 Asset 하나의 형식 오류가 전체를 막는다. 바꾼 뒤에는 DagBag 오류가 0인지 먼저 확인했다(결정 70). 깨진 약 5분 동안 스케줄러가 밀린 작업(molit_rent, seoul_api)을 시작하려다 "Dag not found"로 못 했고, 고친 뒤 다시 돌아 둘 다 성공했다.
    - **부수 효과 (사용자에게 알릴 것):** 시험하려고 Airflow를 띄우자 꺼져 있던 동안 밀린 정기 실행이 돌았다(catchup=False라 가장 최근 한 구간만). `seoul_api`와 `molit_rent`의 2026-11-09 구간이 실제 API를 호출해 수집했고, 그 Asset으로 `wh_load`가 한 번 더 돌아 wh·mart와 `product/v2026.11.13`이 새로 만들어졌다. 사용자가 정해 둔 일정 그대로의 실행이고 멱등이지만, 내가 지시받지 않은 수집이 돌았다.
18. **MCP SDK는 2.x(MCPServer)로 갔다.** 설계서의 FastMCP는 1.x 이름이다. 새로 쓰는 코드를 옛 판에 묶지 않았다(결정 69).
19. **MCP 확인 스크립트는 `tests/check_*.py`로 두어 CI에서 빠지게 했다.** CI는 `tests/test_*.py`만 돌리고 DB가 없다. 이 확인은 DB와 lineage 회차가 있어야 한다.
20. **변이는 stg 복사 대신 뷰로 걸었다.** 생활이동 stg가 4천만 행이라 변이마다 복사하면 디스크와 시간이 크게 든다. `stg_mut`에 원본을 읽는 뷰를 두고 변이 컬럼만 식으로 바꿨다. 실제 stg·wh·mart는 읽기만 했고 끝나면 `stg_mut`, `wh_mut*`, `mart_mut*`를 지웠다.
21. **비교 기준을 실제 mart가 아니라 대조군 빌드(M0)로 잡았다.** 밤사이 Airflow가 수집을 돌리면 stg와 mart가 어긋날 수 있다. 실제로 첫 시도에서 그랬고, 대조군 검사가 잡아 멈췄다. 변이 결과는 같은 stg에서 같은 방법으로 만든 M0과 비교해야 공정하다.
22. **dbt 컴파일 결과를 `target/mut`에 따로 썼다.** lineage DAG는 `target/`의 manifest와 컴파일 SQL을 읽는다. 변이 빌드가 그것을 덮으면 지도가 `wh_mut` 이름으로 만들어진다.
23. **혼잡도 이전에서 Python 경로를 지우지 않았다.** 설계서 2.6 5번은 같음이 증명되면 은퇴시키라고 하지만, `measure/change_cost.py`(측정 13 재현)가 옛 모듈을 부르고 옛 표를 지울지는 사용자가 정하게 되어 있다. DAG에서는 빠졌으므로 더 이상 돌지 않는다. 남은 파일: `transform/congestion.py`, `tests/test_congestion.py`(CI에서 계속 통과), `warehouse/sql/03_stg_congestion.sql`, 표 `stg.congestion`(325,845행, 더 갱신되지 않음).
24. **운영 뷰는 stg_dbt를 이름으로만 부르게 했다.** 교체 매크로의 `drop schema ... cascade`가 의존 뷰를 함께 지운다는 것을 이전 전에 알아챘다(결정 71 4번). 고치지 않았으면 첫 wh_load 뒤 `ops.quality`가 사라졌을 것이다.
25. **원천 키 매크로를 별칭 묶음으로 바꿨다.** 설계서의 "키 목록 한 곳"만으로는 개명 때 CF1 테스트가 옛 이름을 요구해 새 수집일에서 계속 실패한다. 묶음으로 두면 고칠 곳이 매크로 한 줄 + 모델 한 줄이고, 묶음 안 이름이 둘 다 있는 행은 실패시킨다(결정 64의 "별칭이 동시에 있으면 실패").
26. **이전 직후 혼잡도 지도가 넓어진 것은 오류가 아니라고 판단했다.** `raw.DOW_SE` → 상품 4개(옛 `stg.congestion.dow` → 1개). 검증 규칙(CV2)이 SQL로 와서 "값이 이상하면 행이 빠진다"가 지도에 나타난 것이다(측정 23).
27. **커밋은 하지 않았다.** 설계서가 커밋을 요구한 정답(921901a) 외에는 사용자가 아침에 보고 정하게 남겼다.
28. **(2026-11-13 아침, 사용자 요청) 교체 실패 주입과 lineage 실패 시험.** 둘 다 실제 스키마와 실제 DAG로 했다. 교체 시험은 `mart_build`만 빼 두고 기본 목록으로 교체를 돌렸고, 실패하면 아무것도 바뀌지 않으니 실제 데이터에 위험이 없다(결정 61). lineage 시험은 코드를 고치지 않고 DB 제약을 잠깐 걸어 실패를 만들었다. 시험 뒤 바로 지웠다(결정 50). 시험하려고 Docker Desktop과 Airflow를 다시 켰다. 이번에는 밀린 정기 실행이 없었다(seoul_api, molit_rent는 다음 월요일).
29. **(2026-11-13 아침, 사용자 요청) Metabase 재설정과 U4.** `python -m warehouse.metabase_setup`으로 카드 13개(새 카드 `13_congestion_change` 포함)를 만들었다. 13개 모두 Metabase API로 실행해 오류 0. 혼잡도 이전으로 바뀐 카드(06 출처별 상태는 raw, 10 출처별 품질은 stg_dbt, `ops.quality`는 `ops.row_count`)도 정상이다. 대시보드의 "조치가 필요한 DAG 2"는 이번 작업과 무관한 기존 상태다(file_living_migration 중지, file_sbiz_store 10-21 실패). `metabase_setup.py`의 `SCHEMAS`에 raw, stg_dbt, lineage를 더하지 않았다. stg_dbt는 빌드마다 새로 생겨 명시 권한이 사라지므로 어차피 기본 권한에 기대야 하고, 지금 기본 권한으로 셋 다 읽힌다.
30. **(2026-11-13 오전, 사용자 선택 A) 전월세 정제도 SQL로** (결정 72). 구현 판단은 위임받아 결정 73에 적었다. 순서: 원본 표·적재기 → 법정동 코드표 → dbt 모델·테스트 → 옛 stg와 대조 → wh_load 교체 → 지도 → S2·S3 재측정.
31. **법정동 코드표를 상가정보 정제에 얹었다** (결정 73 1번). 새 파일을 만들지 않고 이미 서울 CSV 전체를 읽는 곳에서 모았다. 옮기기 전에 같은 zip에서 충돌(한 이름에 코드 둘)이 0인지 먼저 셌다. 충돌이 있었다면 기본 키가 상가정보 적재를 막았을 것이다.
32. **첫 대조에서 27행이 달랐고, 원인을 찾아 SQL을 Python에 맞췄다.** 옛 결과를 정답으로 보는 것이 설계서 2.6의 같음 증명이다. 건물 이름 끝의 전각 공백이었고, Python `strip()`의 공백 29글자를 그대로 옮긴 매크로를 만들었다. 혼잡도에도 같은 차이가 숨어 있을 수 있어 같은 매크로로 바꿨다(지금 데이터로는 차이 0, 측정 24).
33. **매크로 파일에 보이지 않는 문자가 들어가 unit test가 깨진 적이 있다.** 셸과 파일 쓰기 도구가 `　` 같은 글자를 실제 문자로 바꿔 넣었고, 그중 줄 구분 문자(U+2028)가 줄을 쪼갰다. 파일을 escape 글자(ASCII)만으로 다시 썼고, 비ASCII가 한글 외에 0인지 확인했다.
34. **정제 뷰가 느려 CTE 두 개를 materialized로 했다** (결정 73 5번). 빌드 52.8초 → 18.8초. 뷰를 표로 바꾸는 쪽은 원본만큼 큰 표가 하나 더 생겨 고르지 않았다.
35. **F2는 가장 최근 단위만, 실패로 두었다** (결정 73 2번). 경고로 낮추면 사람에게 닿는 길이 아직 없다(P7 전). 대가(한 단위가 넘으면 wh_load 전체가 멈춤)와 푸는 법(규칙 고치기 또는 그 단위 원본 지우기)을 테스트 주석과 결정에 적었다.
36. **molit_rent DAG를 Airflow로 돌리지 않았다.** 돌리면 공공데이터포털 API를 실제로 호출한다. 바뀐 것은 정제 명령 한 줄(`transform.rent` → `transform.rent_raw`)이라, 같은 명령을 컨테이너에서 돌리고(멱등 확인) DAG import 오류 0을 확인하는 데서 멈췄다. 다음 월요일 정기 실행이 첫 Airflow 실행이다.
37. **옛 전월세 Python 경로를 지우지 않았다** (혼잡도와 같은 이유, 결정 72). DAG에서는 빠졌다. `stg.rent`(450,957행)는 더 갱신되지 않는다. 측정 스크립트 2개와 `sbiz_store.py`(`insert_sql`)가 옛 모듈을 쓴다.

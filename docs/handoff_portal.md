# 지시서: 데이터 포털 마무리, 그리고 처음 보는 사람도 읽을 수 있게 고치기

Claude Code가 읽고 처음부터 끝까지 진행하는 지시서다. 2026-11-22에 썼다.

## 진행 방식 (사용자 지시 2026-11-22. 이 지시서 범위에서는 CLAUDE.md 1절의 2·3·4·5번 대신 이 방식을 따른다)

1. **승인을 기다리지 않는다.** 단계 사이에 멈추지 않고 끝까지 진행하고, 마지막에 한 번 보고한다(6절 형식).
2. **간단한 일은 바로 한다.** 문구 고치기, 문서 맞추기, 버그 고치기, 시험 더하기처럼 방법이 하나로 정해지는 일은 비교 없이 한다.
3. **고를 것이 있으면 후보를 두고 비교한 뒤 직접 고른다.** 엔진, 라이브러리, 배포 방식, 데이터를 둘 위치처럼 방법이 둘 이상인 일이 여기에 해당한다. 당근 테크 블로그의 도입기처럼 쓴다.
   - 문제: 무엇을 풀려는지 한두 줄
   - 후보: 2~4개. "아무것도 더하지 않기"도 후보에 넣는다
   - 평가 기준: 이 프로젝트에 맞는 것(같은 입력이면 같은 바이트, 서버 없음, 의존성 수, 이미 레포에 있는 것, 이용조건, 처음 보는 사람이 쓰기 쉬운지)
   - 후보별 근거: 공식 문서(URL과 확인 날짜), 레포 파일과 행, 직접 돌린 실측(명령과 결과)
   - 고른 것과 이유, 버린 후보마다 버린 이유
   - 검증: 고른 뒤 실제로 확인한 결과

   비교는 `docs/decisions.md`에 결정 형식(상황, 선택지, 결정과 이유, 검증, 결과와 남은 것)으로 남긴다. 결정 머리에 "사용자 위임(2026-11-22 지시), Claude Code가 고름"이라고 적는다.
4. **모든 작업과 주장에 근거를 붙인다.**
   - 문서와 화면에 쓰는 설명, 숫자, 판단마다 근거를 단다: 파일과 행, 측정 번호, 결정 번호, 실행한 명령과 결과, 공식 문서 URL.
   - 근거가 없으면 먼저 직접 확인한다(파일 읽기, 실행, 공식 문서 찾기).
   - 그래도 확인할 수 없을 때만 `[확인 필요]`로 두고, 막힌 이유를 적은 뒤 다른 일을 계속한다.
   - 추측을 사실처럼 쓰지 않는다.
5. **그래도 사용자 손이 필요한 것**(하지 않고 보고에 적는다):
   - 커밋과 푸시
   - 파일 지우기
   - 공개 범위를 바꾸는 이용조건 판정(`public_columns.json`의 `public` 값)
   - 돈이나 계정이 드는 일

## 0. 한 줄 요약

공개 사이트(https://sozerong.github.io/home_in_seoul-data/)가 "표와 링크만 있는 페이지"에서 "데이터 포털"로 바뀌었다. 이번 일은 세 가지다.
1. 바뀐 내용에 맞춰 문서를 고친다.
2. 글만 읽는 도구(에이전트, 검색엔진)도 사이트 내용을 볼 수 있게 한다.
3. 데이터를 처음 보는 사람도 이해할 수 있게 화면의 말과 설명을 고친다.

## 1. 무엇이 이미 바뀌었나

클라우드 Claude가 아래 두 파일을 레포에 넣었다(커밋 전).

| 파일 | 전 | 후 |
|---|---|---|
| `warehouse/site/index.html` | 없음 | 새로 만든 한 페이지 포털. 서버 없이 브라우저에서 돈다 |
| `warehouse/publish_site.py` | index.html을 파이썬으로 직접 만들고 sql.html을 복사 | index.html은 위 파일을 그대로 복사. `profiles/<버전>.json`(컬럼 프로필)을 새로 쓰고, catalog.json에 표 한글 이름(title), 표끼리 잇는 키(relations), 프로필 위치(profiles)를 더 씀. sql.html은 새 SQL 화면(`index.html#/sql`)으로 넘기는 짧은 파일 |
| `warehouse/site/sql.html` | SQL 화면 | 이제 쓰지 않음(지워도 됨) |

포털 화면 구성(`docs/handoff_pages.md` 8절에 자세히 있음):
- **데이터 목록:** 표 카드, 신선도, 표끼리 잇는 키, 품질 지표, 검색
- **표 화면 탭:** 개요, 스키마, 미리보기, 프로필, 가져가기, 버전
- **SQL 편집기:** 예시 질의, 정렬, 차트, CSV 내려받기, 실행 계획, 링크 복사, 최근 질의
- **출처·이용조건**

동작 방식:
- 화면은 `catalog.json`, 버전마다의 `manifest.json`, `profiles/<버전>.json`만 읽는다.
- SQL과 미리보기는 브라우저 안 DuckDB-WASM이 공개 Parquet를 직접 읽는다. DuckDB-WASM 엔진은 jsDelivr CDN에서 받는다.

확인된 것과 아직 안 된 것:

| 항목 | 상태 |
|---|---|
| 컨테이너에서 `--selftest` | 통과 |
| 로컬 서버 + headless Chrome으로 화면 전체 확인 | 콘솔 오류 0 |
| 실제 Pages 주소에서, CDN에서 받은 엔진으로 확인 | **아직 안 함** |

## 2. 지킬 것

- 공개 버전 폴더(`v2026.11.16/`)의 파일은 바꾸지 않는다(불변). 바뀌는 것은 사이트 파일(index.html, catalog.json, profiles/, sql.html, NOTICE.md, latest.json)뿐이다.
- 설명을 지어내지 않는다. 뜻은 `docs/data_contract.md`, 기존 결정·측정 문서, 직접 실행한 결과에서만 가져오고 근거를 단다.
- 비공개 컬럼(`public_columns.json`의 `"public": false`)은 어떤 화면·파일에도 값을 내지 않는다. 이름과 빼는 이유만 보여 준다.
- em dash(긴 줄표) 기호를 쓰지 않는다. 서버를 만들지 않는다. 새 의존성은 맨 위 "진행 방식" 3번의 비교를 거친 뒤에만 더한다.

## 3. 단계

### 단계 Q0. 받은 변경 확인

- 할 일: Windows `.venv`에서 아래를 돌린다.
  ```
  python -m warehouse.publish_site --selftest
  python -m warehouse.publish_site --version v2026.11.16 --out <빈 폴더 A>
  python -m warehouse.publish_site --version v2026.11.16 --out <빈 폴더 B>
  ```
  A와 B의 모든 파일 sha256이 같은지 본다. 같으면 "같은 입력이면 같은 바이트"라는 성질이 지켜진 것이다.
- 로컬에서 화면을 보고 싶으면 범위 요청(HTTP Range)을 지원하는 서버를 쓴다(예: `npx http-server <폴더> -p 8765`). 파이썬 기본 `http.server`는 범위 요청을 지원하지 않아 SQL 화면이 실패할 수 있다.
- 확인(직접): selftest 출력과 두 폴더 sha256 비교 결과를 보고에 붙인다.

### 단계 Q2. 글만 읽는 도구도 내용을 보게 하기

- **왜:** 새 index.html은 JavaScript로 화면을 그린다. 그런데 JavaScript를 돌리지 않는 도구(웹 페이지를 글로만 받는 에이전트, 검색엔진, 일부 사내 프록시)는 빈 화면을 받는다. 지금은 `<noscript>` 안내 한 줄뿐이다. 단계 P5의 "작업 PC 밖 에이전트"도 이런 도구일 수 있다. 실제로 클라우드 Claude의 웹 읽기 도구는 JavaScript를 돌리지 않는다.
- **고르는 일(3번 방식으로 비교):** 글만 읽는 도구에게 내용을 주는 방법. 후보 예:
  - (가) 만들 때 index.html 안에 요약 HTML을 넣고 JavaScript가 덮어쓰기
  - (나) `<noscript>` 안에 요약 넣기
  - (다) 따로 글 파일(`llms.txt`나 `index.txt`)을 두고 링크
  - (라) 아무것도 안 하고 `catalog.json` 링크만 두기
  
  비교할 것은 에이전트·검색엔진이 실제로 무엇을 읽는지, 같은 입력이면 같은 바이트인지, 코드량이다. 근거로 공식 문서와 직접 실험(`curl`, JavaScript를 끈 headless 브라우저)을 쓴다.
- **할 일(가를 고른 경우의 예):**
  1. `warehouse/site/index.html`의 `<main id="main">` 안에 자리표시 `<!--STATIC_SUMMARY-->`를 둔다.
  2. `publish_site.py`가 복사할 때 그 자리에 평범한 HTML 요약을 넣는다:
     - 최신 버전, 만든 시각
     - 표마다 한글 이름, 한 행의 뜻, 행 수, Parquet·CSV 링크, 컬럼 이름과 한글 이름
     - `catalog.json`·`latest.json`·`NOTICE.md` 링크
  3. JavaScript가 시작하면 이 내용을 지금처럼 포털 화면으로 바꾼다(이미 `#main`을 덮어쓰므로 추가 코드는 거의 없다).
  - 요약도 같은 입력이면 같은 바이트여야 한다(시각을 새로 찍지 않음).
- **확인:**
  - `curl -s <사이트>/ | grep -c "dong_profile.parquet"`가 1 이상인지 본다.
  - selftest에 "index.html 정적 요약에 모든 공개 파일 링크가 있고, 비공개 컬럼 이름 외의 값이 없다" 검사를 더한다.
- 확인(직접): JavaScript를 끈 headless 브라우저로 연 화면, 그리고 `curl` 결과를 보고에 붙인다.

### 단계 Q3. 컬럼마다 쉬운 말 사전 만들기

- **왜:** 지금 화면의 컬럼 설명은 `data_contract.md` 3절 표에서 그대로 가져와, 처음 보는 사람에게 어렵다.
  - 여러 컬럼을 한 줄로 묶어 설명해 "(한 줄로 함께 설명: dong_id, mois_dong_cd, dong_nm)" 같은 꼬리가 붙는다.
  - `monthly_median_rent_10k_won` 같은 이름만으로는 단위(만원)를 알기 어렵다.
  - `offi`, `rh`, `basis` 같은 코드 값의 뜻이 화면에 없다.
- **고르는 일(3번 방식으로 비교):** 쉬운 설명을 어디에 둘지. 후보 예:
  - (가) `public_columns.json`에 필드 더하기
  - (나) `data_contract.md` 3절을 컬럼별 표로 바꾸고 거기서 읽기
  - (다) 새 파일 하나
  
  기준은 원본이 한 곳인지, 계약 문서와 어긋날 위험, selftest로 빠짐을 잡을 수 있는지다.
- **할 일(가를 고른 경우의 예):** `docs/public_columns.json`의 컬럼마다 아래 필드를 더한다.

  | 필드 | 뜻 | 예 |
  |---|---|---|
  | `label` | 짧은 한글 이름(단위 포함) | "월세 중앙값(만원)" |
  | `help` | 처음 보는 사람용 1~2문장. 무엇을 셌는지, 기간, 주의할 점 | "최근 6개월에 새로 맺은 월세 계약의 월세를 줄 세웠을 때 가운데 값. 평균보다 큰 값 몇 개에 덜 흔들린다. 계약이 없으면 비어 있다." |
  | `unit` | 단위. 없으면 빈 글자 | "만원", "분", "m", "건", "%" |
  | `values` | 코드 값 풀이(있을 때만) | `{"offi": "오피스텔", "rh": "연립다세대"}` |
  | `example` | 실제 값 한두 개(이 버전 프로필의 자주 나오는 값이나 중앙값에서) | "58" |

- **쓰는 규칙:**
  - 한 문장은 40자 안팎으로 쓴다.
  - 전문 용어는 풀어 쓴다(아래 표).
  - 숫자는 문서나 프로필에 있는 값만 쓴다.
  - 묶어서 설명하던 컬럼은 하나씩 따로 쓴다.
- **특히 헷갈리기 쉬운 컬럼**(빠짐없이 다룬다):
  - 코드 세 가지 차이: `dong_id`(통계청 동 코드, 표끼리 잇는 키), `mois_dong_cd`(행정안전부 동 코드, 다른 시스템과 맞출 때), `sgg_cd`(통계청 구 코드. 강남구는 11230이고, 행정안전부식 11680과 다름)
  - `*_10k_won`: 만원 단위
  - `avg_minutes*`: 생활이동의 평균 이동 시간. 머문 곳 기준이라 가까운 동일수록 실제보다 길게 나온다(계약 6절 1). 대중교통 길찾기 시간이 아니다.
  - `population_*`: 가중 평균이라 소수점이 있다. 3명 이하 이동은 가려져 빠진다(계약 6절 4).
  - `basis`, `copied_from_2021_split_dong`, `target_months`, `distance_km`(직선거리)
  - `monthly_deals`·`jeonse_deals`: 최근 6개월, 오피스텔·연립다세대만. 다가구 원룸은 빠진다(계약 6절 2).
  - `dong_mois_map`의 `is_primary`, `stores`, `share`
- `publish_site.py`가 이 필드를 catalog.json 컬럼에 넣는다.
- selftest에 두 검사를 더한다.
  - 모든 공개 컬럼에 `label`과 `help`가 있다.
  - `values`의 키가 이 버전 프로필의 실제 값에 있다. 없는 코드를 풀이하지 않게 하기 위해서다.
- `help`마다 근거를 남긴다(예: `"source_ref": "data_contract.md 6절 1"`). 계약 문서, 결정, 측정, 매뉴얼 요약(`docs/seoul_living_mobility_manual.md`), 프로필 값에서 찾는다. 그래도 근거가 없으면 `[확인 필요]`로 두고 보고에 목록으로 적는다.
- 확인(직접): selftest 통과. 단계 Q6 시험에서 "뜻을 몰랐던 말"로 나온 컬럼을 고친다.

### 단계 Q4. 표마다 "쓰기 전에 알아 둘 것"

### 단계 Q5. 화면의 말을 쉬운 말로, 처음 온 사람 안내 더하기

`warehouse/site/index.html`에서 아래 말을 바꾼다. 처음 나올 때만 괄호로 원래 용어를 남겨, 아는 사람도 찾을 수 있게 한다.

| 지금 | 바꿀 말 |
|---|---|
| 결측 | 비어 있는 값(결측) |
| 고유값 | 서로 다른 값 수 |
| 사분위 25 · 50 · 75 | 하위 25% · 가운데 · 상위 25% 값 |
| 히스토그램 | 값 분포 |
| 한 행을 가르는 컬럼 | 한 줄을 구분하는 값(키) |
| 한 행 = … | 이 표의 한 줄은 …입니다 |
| sha256 | 파일 지문(sha256): 내려받은 파일이 원본과 같은지 확인하는 값 |
| manifest.json | 버전 설명서(manifest.json) |
| 격리 행 | 검사에서 걸러 따로 둔 행(상품에는 없음) |
| 실행 계획 | 실행 계획(어디서 시간이 걸렸는지) |
| Parquet / CSV | Parquet: 분석 도구용(타입이 유지되고 작음) / CSV: 엑셀용 |

더할 것:
1. **처음 오셨나요 페이지(`#/help`)와 홈 맨 위 안내 카드.**
   - 이 데이터가 무엇인지 한 문단
   - 쓰는 순서 3단계: 표 고르기 → 스키마에서 컬럼 뜻 보기 → SQL로 뽑거나 파일 내려받기
   - 용어 풀이 표(위 표의 말들, dong_id, 중앙값, 버전)
   - 자주 묻는 질문 5개. 답은 계약 문서와 결정 문서에 있는 내용만 쓴다.
     - 왜 동 이름으로 표를 이으면 안 되나(같은 이름의 동이 여럿)
     - 왜 출퇴근 시간이 길게 나오나
     - 왜 일부 컬럼이 없나(이용조건)
     - 데이터는 언제 바뀌나(갱신 주기, 계약 1절)
     - 엑셀에서 코드 앞의 0이 사라질 때
2. **화면 전체에 컬럼 한글 이름(`label`)을 먼저, 영문 이름을 작게 보여 준다.** 스키마·프로필 탭, SQL 편집기 왼쪽 목록이 대상이다. SQL 편집기는 영문 이름을 넣고, 마우스를 올리면 `label`과 `help`가 보이게 한다.
3. **예시 질의마다 "이 질의가 답하는 질문" 한 줄을 붙인다.** 예: "구마다 오피스텔 월세가 가운데쯤 얼마인가". 예시 고르기 목록에 보이게 하고, SQL 안 주석도 쉬운 한국어로 쓴다.
4. **품질 지표마다 "이 숫자가 뜻하는 것" 한 줄.** 예: 월세 계약이 없는 동 15곳은 월세 중앙값이 비어 있다.
5. **SQL 오류가 나면 흔한 원인 안내를 오류 아래에 덧붙인다.**
   - 표·컬럼 이름 오타: 왼쪽 목록을 누르면 들어간다
   - 글자 값은 작은따옴표로 감싼다
   - 코드 값 비교는 '11230'처럼 글자로 한다

- SQL 편집기에 문법 강조나 자동 완성을 넣고 싶으면 3번 방식으로 비교한다. 후보에는 "지금처럼 textarea"를 넣고, CDN 의존성이 하나 늘어나는 비용도 적는다.
- 확인(직접): 홈, `#/help`, 표 하나의 스키마 탭, SQL 편집기를 headless 브라우저로 찍고 콘솔 오류 수를 적는다. 자주 묻는 질문의 답마다 근거 문서와 절을 적는다.

### 단계 Q6. 처음 보는 사람 시험

### 단계 Q6b. SQL 엔진(DuckDB-WASM)을 어디서 받을지 비교

- **문제:** 지금은 jsDelivr CDN에서 `@duckdb/duckdb-wasm@1.33.1-dev57.0`을 받는다. 이 판은 npm 태그 latest이지만 이름에 dev가 붙어 있다(2026-11-22 `npm view` 확인). CDN이 막힌 환경에서는 SQL 화면만 동작하지 않는다.
- **후보:**
  - (가) 지금처럼 jsDelivr, 판 고정
  - (나) unpkg 등 다른 CDN
  - (다) 엔진 파일을 데이터 레포에 같이 올림. Pages는 게시 사이트 1GB 한도가 있고, eh 판 wasm 하나가 약 36MB다
  - (라) 정식 판으로 고정
- **근거로 볼 것:**
  - DuckDB 공식 문서의 WASM 배포 안내
  - GitHub Pages 한도 문서
  - 각 판으로 예시 질의 7개를 돌린 결과와 첫 로딩 시간(headless 브라우저, 3회)
- **기록:** 고른 것을 decisions.md에 남기고, 측정은 `docs/measurements.md`에 조건과 함께 적는다.

## 4. 끝난 기준

| 기준 | 확인 방법 |
|---|---|

| 모든 공개 컬럼에 한글 이름과 쉬운 설명이 있음 | selftest 통과(새 검사 포함) |

## 5. 하지 않는 것

- 공개 버전 폴더의 파일, `product/`, 운영 DAG는 건드리지 않는다.
- 비공개 컬럼을 "설명용"으로라도 값과 함께 보여 주지 않는다.
- 근거 없는 설명이나 숫자를 쓰지 않는다. 먼저 직접 확인하고, 그래도 모르면 `[확인 필요]`로 둔다.
- 서버와 로그인은 더하지 않는다. 새 라이브러리나 CDN은 3번 방식으로 비교해 이득이 근거로 보일 때만 더한다.
- 브라우저 안 SQL의 범위 요청 실측은 이번 범위가 아니다. 측정 56의 "한계"에 남은 일로 이미 적혀 있다.

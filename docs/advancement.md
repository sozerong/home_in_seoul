# 고도화 기록

단계 0~10을 마친 파이프라인을 실무형 구조로 키워 가는 과정을 처음부터 끝까지 이어 적는다. 결정 하나하나는 decisions.md, 수치는 measurements.md에 있고, 이 문서는 그 둘을 "왜 이 순서로 무엇을 바꿨고 무엇을 얻었나"로 묶는다. 방향과 순서는 결정 28.

## 1. 동기

- 목표: 실무에서 쓰는 대용량·분산 처리 기술을 직접 다뤄 보는 것(학습).
- 출발점의 판단: 지금 규모에서는 Spark·DuckDB가 필요 없다(결정 24, 측정 5). 그래서 "필요해서 도입했다"고 쓰지 않는다. 기록된 문제에 연결하고, 도입 전후를 실측해 이점이 있었는지 없었는지를 숫자로 남긴다.

## 5. 단계별 기록

각 단계가 끝나면 아래 형식으로 적는다: 무엇을 바꿨나 / 전후 수치 / 얻은 것 / 얻지 못한 것.

### 단계 1. wh_load 중복 실행 정리 (2026-11-03)
- 무엇을 바꿨나: seoul_api의 두 수집·정제 작업이 각자 내던 Asset 알림을, 둘 다 끝난 뒤 도는 작업 `stg_updated` 하나가 함께 내도록 했다(dags/seoul_api.py, 결정 29).
- 전후 수치: seoul_api 한 번에 이어지는 wh_load 실행이 2번 → 1번. 수동 실행 1회로 확인(13:47, wh_load 110.7초). 정기 실행 기준 주 3회 → 2회는 11-09에 확인한다.
- 얻은 것: 주당 wh_load 약 1.8분 1번의 중복 제거. 원인을 추측하지 않고 Airflow 메타데이터(`dagrun_asset_event`)로 실행마다 어느 알림이 붙었는지 확인하는 방법.
- 얻지 못한 것: 정기 실행이 PC 절전으로 늦는 문제(P3)는 그대로다(11-02도 6시간 39분 지연). 단계 3에서 다룬다.

### 단계 2. dbt (2026-11-03)
- 무엇을 바꿨나:
  - warehouse/sql 07~09(wh DDL, wh 적재, 마트)를 dbt 프로젝트 warehouse/dbt로 옮기고 지웠다. 모델 17개(wh 테이블 7, 뷰 3, mart 7), 손 대응표 seed 2개, 테스트 65개.
  - 검사: 07의 PK·FK·NOT NULL·CHECK와 08·09의 구조 검사 8개를 모두 dbt 테스트로 옮겼다.
  - 실행: wh_load가 빌드용 스키마(wh_build, mart_build)에 만들고, 테스트를 모두 통과하면 한 트랜잭션으로 wh·mart와 교체한다(blue/green).
  - dbt는 Airflow 이미지 안 전용 가상환경(dbt-core 1.12.6, dbt-postgres 1.11.0).
- 전후 수치(측정 8):
  - 결과: wh 10개, mart 7개 모두 두 방향 EXCEPT ALL 차이 0, 컬럼 타입·순서 차이 0. 상품 파일 8개는 내용이 같다.
  - 시간: 변환 89.5~104.7초(08+09, 8회) → 66.1~68.8초(dbt_build+swap, 3회). 실행 전체 101.9~118.5초 → 78.6~83.3초.
- 얻은 것:
  - 실행 순서를 사람이 아니라 dbt가 `ref()`로 정한다.
  - 손으로 정한 대응이 SQL 안 VALUES가 아니라 CSV로 분리되어 바꾼 이유(note)까지 DB에 보인다.
  - 검사가 실패하면 실제 wh·mart와 상품은 그대로다(실패 주입으로 확인, 결정 32).
  - 검증 중 rent_listing 상품 파일의 행 순서가 실행마다 바뀌는 문제(원래 있던 비결정적 정렬)를 찾아 고쳤다(결정 33). 이제 같은 데이터면 같은 sha256이 나온다.
- 얻지 못한 것·대가:
  - wh 테이블의 DB 제약(PK·FK)이 사라졌다. pgAdmin에서 손으로 넣는 잘못된 행은 DB가 막지 못하고 다음 빌드 때 덮인다.
  - dbt v2(Rust 엔진)는 PostgreSQL을 지원하지 않아 v1을 쓴다. 새 기능은 v2에만 들어간다(결정 30).
  - 시간이 준 이유(threads 4의 동시 빌드인지)는 나눠 재지 않았다.
  - docs/architecture.svg·png는 아직 08·09 기준 그림이다.

### 단계 3. 운영: CI와 정기 실행 시각 (2026-11-03)
- 무엇을 바꿨나: 푸시·PR마다 단위 테스트와 `dbt parse`를 돌리는 GitHub Actions(.github/workflows/ci.yml). 정기 실행을 PC가 켜져 있는 월요일 13:00·13:30, 매월 21일 13:00으로 옮겼다(결정 34).
- 전후 수치: 예정 시각에 돈 정기 실행 0회(3주 연속, 지연 약 6시간)는 11-09부터 다시 센다(측정 7). CI 소요 시간은 첫 실행 후 적는다.
- 얻은 것: 깨진 정제 규칙, dbt의 ref·YAML 오류가 다음 정기 실행이 아니라 푸시 순간에 드러난다. dbt parse가 DB 없이 된다는 것을 확인해 CI가 비밀 값 없이 돈다.
- 얻지 못한 것: DAG 문법 오류와 모델 SQL 실행 오류는 CI가 잡지 못한다(S3-1 A, C). PC가 꺼진 주에는 여전히 밀린다(근본 해결인 VM은 4단계 뒤에 다시 본다). 일정을 바꾸면 Airflow가 지난 회차를 바로 돈다는 것을 실행으로 알게 됐다.
